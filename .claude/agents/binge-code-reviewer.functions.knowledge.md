### Hooks, effects & closure safety
- **A LAYOUT-level "replace the whole app" branch keyed on a context flag unmounts the component that reports the operation's outcome.** BIN-816 flipped `setDeletionInProgress(true)` at the START of `deleteAccount()`, so `AppShell` swapped to `DeletionLimbo` while the cascade still ran: `DeleteAccountSection` unmounted, its catch-block toast landed over a screen asserting the opposite, and the retry `onClick` (`setConfirming(true)`) became a no-op on an unmounted component — a required affordance that only its own `useAuth`-mocking unit test can see. Ask WHERE the flag flips relative to the messages and callbacks it invalidates, and whether the replacement screen's copy is true at the EARLIEST moment it can render (here "vi hann ta bort din data" shows before anything is deleted). Providers mounted ABOVE the shell keep running, so "a surface that is never rendered cannot write" is false whenever a context above it writes on snapshot (`WatchlistContext`'s notes migration + addedAt repair). **The same question run at the START of the operation: a step PREPENDED to a cascade silently falsifies the failure CLASSIFIER's premise about what has been written by the time it runs.** `classifyDeletionFailure`'s `untouched` branch — "Ingenting har raderats", one of four legally-approved strings — is defined as "every remaining path, all of which run before the first write", and the [UX] accepted deviation's whole scope rests on that ("a failure on the very first commit … data was never touched"). BIN-1063 steg 3 put `await handOverOwnedGroups()` first in `runDeletionCascade`: a SERVER-side loop that hands groups over one at a time, counts a per-group failure and keeps going, then throws — so `failed > 0` routinely coexists with irreversible commits (ownership transferred, `members`/`household`/`joinAttempts`/`progress` deleted, `addedBy` cleared), and its `HttpsError` carries none of the three tags, so it classifies `untouched` and the user is told nothing was deleted. Only `applyDeletionPlan` tags `CASCADE_PARTIAL`; anything inserted ahead of it inherits the untagged branch by default. So whenever a diff adds a WRITING step before the first tagged writer, check the classifier's branch list and the strings each branch prints — and price the reachability from the callable's own limits (no `timeoutSeconds` on `onCall` = 60 s over an unbounded per-watchlist-item write loop). Fixing the code and leaving the classifier's docstring is half the change; fixing the docstring alone is the strike-rule reword that ships the lie. **And the tag can only ever cover the failures the step RETURNS from, so the absolute stays false and must be STRUCK rather than defended.** The r2 fix was right — a server-side `attempted` counter incremented BEFORE the first write of a group (never after the last, because a chunked erasure commits then throws), a marker in the refusal only when `failed > 0 && attempted > 0`, mapped client-side to `markCascadePartial` — but a callable that DIES mid-loop returns no summary and emits no marker: `onCall` defaults to `timeoutSeconds: 60` and the write count grows with every owned group's watchlist, so deadline-exceeded on exactly the heavy account BIN-876 was written about lands back in `untouched`. No `timeoutSeconds` can close it (an instance kill is always available), so the durable answer is to strike the "all of which run before the first write" clause, not to raise a number. Ask of any such tag: which failures never reach the code that sets it? **And raising a callable's `timeoutSeconds` past the CLIENT's own default inverts who gives up first — measured, not recalled: `node_modules/@firebase/functions/dist/index.cjs.js:628` is `const timeout = options.timeout || 70000`, a `Promise.race` against `failAfter` that abandons the promise without aborting the request.** r3 set `timeoutSeconds: 300` on the callable and passed no `{ timeout }` to `httpsCallable`, so between 70 s and 300 s the client throws `deadline-exceeded` — carrying none of the tags, hence `untouched` and "Ingenting har raderats" — on a call the server is still running and will usually finish. Data stays safe (idempotent, the retry converges) and the message is the same lie, newly reachable, created by the fix for it. Whenever a diff moves a server-side timeout, grep the call site for a client-side one and say which side now fires first.

### Cloud Functions: notify contracts, sweeps, budgets
- **Per-user error isolation is the house pattern** — `Promise.allSettled` + per-item try/catch, skip-key added BEFORE the try. An unguarded loop lets one failing push abort every later title; a DATE-gated trigger makes the miss PERMANENT.
- **The inbox card is written on the FEATURE opt-in, never gated on `pushEnabled`** — that flag only decides whether FCM fires; coupling them hides the event from everyone without push (default false).
- Dedup is per-USER, not per-title: a `{tmdbId}`-keyed marker skips EVERY owner on a same-day rerun — use `inboxRef.get().exists`. Contract = at-most-once push, exactly-once inbox: marker AFTER content-check+inbox-write; inbox doc = deterministic id + `merge:true`; an empty week never burns it.
- Full-scan pagination: cursor = last doc of the PAGE (never last patched/orphan doc) or the scan wedges; terminate on `snap.empty` OR `snap.size < PAGE_SIZE`. Budget canon: count + `alertedAt`/`capLoggedAt` in ONE transaction, side effects after; MOTN's day key is UTC; a slot is never refunded.
- **Per-chunk rollback must be scoped to "this chunk onward"** — an outer catch assuming nothing committed un-marks committed chunks. Same split in the AUDIT: a VERDICT counter AND a COMMITTED one; one counter makes a mid-page failure contradict its own breakdown. A merge-written audit with an omitted `error` key leaves a prior `error: true` forever.
- `AbortSignal.timeout` covers fetch initiation + headers, NOT `res.json()`'s body. Functions can't import `@/lib/tmdb/providers.ts` — the alias mirrors (`availableNotify/logic.ts`, `insights/rollup.helpers.ts`) must stay in sync with `SWEDISH_PROVIDERS`.

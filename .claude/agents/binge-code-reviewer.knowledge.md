## Principles

### Review process & verification discipline
- **The staged index is ground truth and it is not stable.** Run `git diff` (worktree-vs-index, no `HEAD`) on every reviewed file and confirm EMPTY; end with `git diff --stat` empty + a test run. `git diff HEAD` merges index+worktree and shows an unstaged fix as present (BIN-540: a re-review passed a diff whose INDEX still had the bug). **A re-review's briefed delta is a CLAIM, not a premise** — `git diff <pinned-sha> <current-sha>` every pinned path yourself. BIN-641 r10 was briefed "two files, comment-only"; five blobs had moved and two carried executable changes. Re-derive them; say plainly the premise was false. **A green `vitest run` proves the WORKING TREE is safe, not the staged commit.** BIN-814's staged product diff added a key to two `refreshTmdbFields` payloads, going stale against two `Object.keys(payload).sort()` assertions in test files that were never staged at all (absent from `git diff --cached --stat`); the first run caught 2 failures, but a concurrent sibling patched both test files live in the working tree between runs, so the second run went green while `git status` still showed them unstaged. Compare `git diff --cached --stat` (files in the commit) against `git status --porcelain` (files touched right now) BEFORE trusting a green run — a fix sitting outside the former still ships red the moment the commit lands, whoever wrote it. **Run the suite even on a diff that adds only NEW files: `docs/org/gen-ownership-map.test.mjs` fails whenever a directory the ownership map lists file-by-file gains an unowned sibling** (BIN-816 added five under `src/lib/**` and left `docs/role-responsibilities.md` unstaged → 2 red; its REMEDIATION round then added a sixth test file and left THAT unowned → the same 2 red, so re-run `node docs/org/gen-ownership-map.mjs --check` after every fix round, never only the first). And `npm run test:rules` is a SEPARATE run the root suite never covers: if port 8080 is held by a sibling's emulator, don't kill it — point your own at another port with a scratchpad `firebase.json` (`--config`, absolute `firestore.rules` path, own hub/logging ports) rather than reporting the rules diff unverified.
- **`git show :<path>` (bare colon = index) is the staged blob.** When worktree and index diverge, test the INDEX (worktree rig below), never the working file. **When NOTHING is staged, `git rev-parse :<path>` returns HEAD's PRE-FIX bytes** — pinning it certifies the opposite of what you reviewed; pin `git hash-object <path>` and say why. Same for a PARTIALLY staged file ("MM"/"AM"): pin and review the index, and NAME the unstaged delta (BIN-596). **A blob-to-blob diff showing a WHOLE-FILE rewrite is usually a line-ending flip, not a rewrite** — the repo has `core.autocrlf=true` and NO `.gitattributes`, so every source blob is LF except any a tool wrote as CRLF; count `\r\n` vs `\n` in `git show :<path>` before reading 250 changed lines (BIN-645's `QuickAddButton.test.tsx` hid a 5-line delta this way and would check out with `\r\r\n`).
- **A concurrent agent shares this tree** — mid-review edits, bytes moved index→worktree, a `git reset` repointing the index, a sibling MUTATION-TESTING the file under review (BIN-641 ×2, BIN-645, BIN-777/646 — mutants those tickets' own tests exist to catch, seen live then self-healed mid-review). Compare with `git hash-object`/`git rev-parse :<path>`, never a raw `md5sum`. If the worktree copy is mutated when you finish, SAY SO: the index is safe but a later `git add -A` would land the mutant (an UNSTAGED reviewed file gets said loudly — re-add by pathspec). **A failing test NAME absent from the staged blob PROVES a foreign edit**, not a flake — so does a failure on a DIFFERENT invariant than the one under review, and strongest of all an OUTPUT the staged source cannot produce (BIN-815 r2). A sibling's mutant restores between runs, so before/after hashes can BOTH read clean; two distinct mutants inside one 4-second suite run is "continuous churn" — go straight to the isolated worktree. **The cheapest tell that the churn is a SIBLING's mutation run: your mutant kills tests for a case it structurally cannot reach** (BIN-815 r3). Don't reason about the anomaly, `git status` it: `MM` on a file you never edited settles it.
- **When the churn is CONTINUOUS the hash-loop can't converge — build an isolated worktree of the INDEX and run there:** `git write-tree` → `git commit-tree $TREE -p HEAD -m snap` → `git worktree add --detach <scratch> $COMMIT`, then give it its OWN deps: `npm --prefix <scratch> ci --prefer-offline --no-audit --no-fund` (~50 s from the npm cache). Verify each `git hash-object` == its staged sha, then run the suite AND every mutation there — the shared checkout is untouched. A private install also isolates the vitest cache for free (default `cacheDir` = `node_modules/.vite`; `--cache.dir` is not a vitest 4 flag). It proves the staged set commits ALONE (typecheck + full suite there); reconcile a differing test count rather than doubting it, and expect FS-walk tests (`design/consistency.test.ts`, 5s timeout) to time out on the slow temp path — environmental, not a diff defect. Costs ~4 min end to end; worth it on any auth/data diff. **REUSING the rig across review ROUNDS is how a clean re-review invents a flake:** re-point it (`git checkout --detach $COMMIT`) AND delete its `cacheDir` — a persistent per-run `cacheDir` serves round N−1's mutant. BIN-679 r2 saw 2 of ~30 runs of the CLEAN staged file fail with output byte-identical to a mutant this rig had built (plus one unexplained self-restore inside the worktree); after clearing it, 27/27 green. A "flake" whose failure output equals one of your own mutants is rig contamination — clear, re-run to double-digit greens, and report the bad runs as rig, not as a test defect.
- **Never dismiss on one run a test failing on the exact assertion a fix targets** — but FIRST rule out a foreign edit (hash the file): successive runs failing on DIFFERENT tests is the tell. Then re-run 5-10×, isolated and as invoked. Flake only after double-digit unchanged passes — name it, don't omit the bad run. **Exceptions that DO resolve fast, both cache-shaped: the run(s) right after `rm -rf node_modules/.vite/vitest`** (BIN-687/688, 2 fails on DIFFERENT assertions then 8/8 — cold-cache jitter) and a stale `cacheDir` replaying a prior round's mutant (see the rig bullet); name the cache timing, don't omit the bad runs. **A one-shot worktree-vs-index divergence that self-heals is the same class**: BIN-646's `git diff` showed the staged deletion re-added, then read clean on the next command with `hash-object == :path` — report the sighting, and settle it with an atomic `grep-assert → suite → grep-assert → git status` in ONE command rather than reasoning about it.

### Firestore doc-ids, indexes & id-scheme migrations
- TMDB movie and TV ids are INDEPENDENT namespaces — collisions are real. Any doc/Map/Set/query key spanning both needs `mediaTypeDocId(mediaType, tmdbId)` or an explicit discriminant.

### Firestore client write-path invariants (incl. freshness stamps)
- A new local constant echoing an existing bound (`MY_GROUPS_LIMIT=100` vs rules-enforced `memberUids.size()>100`) imports the authoritative one.

### Provider catalog / cost model (money)
- **Unknown-provider cost in any RANKING context must be `?? Number.POSITIVE_INFINITY`** (sorts last), NEVER `?? 0`, which makes an uncatalogued paid service win as "free". That is a correctness bug; the owned-service short-circuit is the only 0-kr path.

### Testing mechanics
- Coverage gaps are `binge-test-reviewer`'s gate (advisory here) — flag one when an invariant was verified by manual trace only.

### Domain gotchas & accepted behaviours (don't re-flag)
- Dates: `new Date(iso + 'T00:00:00')` = LOCAL midnight, an established idiom (advisory only). `stockholmDayId` is the canonical day key, never `toISOString().slice(0,10)`. TMDB `release_date` is a CALENDAR date — `slice(0,10)` behind a `length>=10` guard, never a tz conversion; persistent cards use time-neutral copy, only same-day push says "idag".
- Deliberate, don't flag: `promptRating` reading `getItem(tmdbId)` before `await addItem`; `availableGenres` from a status-only base set; `QuickAddButton` omitting `totalSeasons`/`tmdbStatus` in markSeen; hardcoded `'movie'` for `/collection/{id}` `parts`; dead exports as forward infra. `<JustWatchCredit />` whenever any provider list is non-empty. `discoverMovies`/`discoverTV` inject `{region:'SE', watch_region:'SE'}` — only flag raw `tmdbFetch`.

## Mutation-testing protocol (the house method)
- **Never mutate `firestore.rules` in place** — killed mid-edit agents have left it broken, and a concurrent session does mutate the SHARED live file mid-review (an unstaged `/* MUTANT: … */`, or a "Change detected, updating rules… WARNING Unused function" on a run where the function should be referenced; RESTORE FROM BACKUP IMMEDIATELY). Use a scratchpad COPY: mutate the copy and run a COPY of the existing test file with its `readFileSync(...)` repointed at the scratch copy. That copy needs its own emulator + config, since `vitest.rules.config.ts`'s `include: ['src/test/rules/**/*.test.ts']` won't pick up a file outside the glob — drop the repointed test INSIDE `src/test/rules/` under a throwaway untracked name with a distinct `PROJECT_ID`, run it via `firebase -c <scratch>/firebase.json emulators:exec --only firestore --project <distinct-id>` on offset ports (8091/4491/4592). **The plain `npm run test:rules` CONTROL run needs the same offset-port treatment whenever a concurrent session holds 8080** — the firestore emulator does NOT no-op on a taken port, it hard-fails with zero tests run and is easy to mistake for a red suite. `md5sum`/`git status --porcelain` the real `firestore.rules` before AND after EVERY run — control and mutant alike — AND once more immediately before writing the verdict. [arkiv 10]
- **A PAIRED growth guard (`hasAll(old)&&size==old+1`) needs a SWAP fixture — drop one old member, add self+a replacement — a size-only or hasAll-only violation leaves the other clause to deny it alone.** BIN-1125's swap fixture closed it, live-verified (dropping `hasAll(old)` on join OR accept alone reddens the swap case). **A fixture's own comment claiming "the only case that isolates X" is a checkable mutation claim — re-check EVERY sibling fixture, including ones in the same diff** (a pre-existing duplicate-of-self pad fixture isolated the same clause identically — struck, not reworded). [arkiv 97] **A hand-copied pin (`ownerUid`/`name`/`defaults` unchanged) repeated across several branches of one `allow update` needs a fixture PER BRANCH** (pre-existing `groups/{groupId}` gap, 2026-09-09). Severity splits on whether an inner guard covers it: an early-out whose write is refused again downstream is a cost-saving LOW; one whose `users/{uid}/watchlist/*` batch has NO second guard is blocking. A shared guard reused at sites with DIFFERENT sibling guards needs a fixture per site (BIN-509). **A handed-down "N red" for a composite guard is ambiguous between "drop one term" and "drop the whole condition" — mutate term-by-term and report the per-term breakdown** (BIN-849). — same in the NEGATIVE direction: a fixture proving exclusion from an AND-gated offender list is vacuous on its target term if a SECOND term already excludes it independently (BIN-1176's `renovate.json` a1Offenders fixture: `tier==='skip'` via an unrelated reasonCode masks removing `isCodePath`) [arkiv 99]. [arkiv 12]

## Sentinel / key-absence assertions & merge-write payloads
- **A rule's `get(k, DEFAULT)` sentinel is untested unless a fixture pairs a MISSING field with a payload equal to the mutated default** — `null`→`''` in `isOwnIdentity` (BIN-1126) stayed 445/445 green. [arkiv 87]

## Firestore rules testing
- Verify `assertFails` cases actually threw `PERMISSION_DENIED` in emulator logs (`--reporter=verbose`) — a silently-vacuous assertFails is indistinguishable from a real deny. Rules value-checks get live-mutation-verified on a scratchpad COPY. Firestore's create-vs-update branch is decided PURELY by `resource == null` at eval time, so a seed-delete-repeat test proves nothing an existing `it.each` row already pins for the same id. **When a create-narrowing diff adds a POSITIVE boundary control, prove the mutant it names is the one it kills WITHOUT touching the tree** (a read-only `node -e` probe of the old/new/slipped regexes over the block's fixture list), and check each file's `initializeTestEnvironment` argument — a suite booting an inline `OPEN_RULES` string is structurally blind to a rules mutant. **A rules regex is quoted VERBATIM in `docs/workflow-map.html`**, which `scripts/check-workflow-map.mjs` cannot see — grep the map for any literal the diff changes and require the map's OWN follow-up commit, never bundled with the rules commit. **A strike is only terminal if the claim did not MIGRATE into the neighbouring sentence.** [arkiv 38]
- **A Cloud Function writing a NEW field onto a `hasOnly()`-gated, client-writable doc needs a SAME-COMMIT rules-whitelist update** — merge-writes evaluate the FULL post-merge doc, so Admin-SDK bypass protects only itself, not the doc's next client write. Shape: seed a post-writer doc, assert an unrelated client write still succeeds (BIN-402).
- Forge-pin idiom: check the REQUEST doc's key presence — `!('f' in request.resource.data) || request.resource.data.f == resource.data.get('f', null)`. The stored-doc idiom (`!('f' in resource.data)`) is forgeable on any doc created before the field existed (BIN-365). An idiom fix across N OR-branches needs a per-branch deny test.
- Attribution: seed every OTHER whitelist condition correctly so a denial is attributable to the guard under test (BIN-24); seed the owner profile for identity-forgery denies so it isn't a null short-circuit. **An UNSEEDED attacker profile doesn't just null-short-circuit `isOwnIdentity` — its `get()` on a nonexistent doc THROWS, masking every guard AFTER it in the `&&` chain** (BIN-1127) [arkiv 100]. Fix and proof are the same fixture: give the attacker a real profile (or send the nullable identity field as `null` to bypass that clause on purpose) so the write reaches the clause under test, then confirm that fixture alone reddens when the named clause is deleted. Multi-branch `allow update`: pair every deny with a positive twin, seed preconditions EXCLUSIVELY so only the target branch is passable, walk every branch (BIN-276).
- Field OMISSION is distinct from wrong-TYPE — implicit fail-closed via `hasOnly()` needs its own test; a shared "valid" positive fixture must INCLUDE every type-guarded field; new stamped fields get the type-reject + future-date-reject pair. **The two also stay distinct PER FIELD when a collection binds N fields with unconditional dot-access (`d.field is T`, no `!('field' in d) ||`)**: one representative field's omission test does not cover the other N-1 — wrapping any ONE of them in an optional guard (`!('f' in d) || d.f is T`) only reddens a fixture that OMITS exactly that field, and the sibling's own wrong-type-when-present `it.each` row stays green under it (that row only exercises presence, not absence). Live-verified BIN-1170: `pauseHistory` pinned `createdAt`'s omission and every field's wrong-type, but making `providerId` optional left all 14 shipped tests — including `providerId`'s own wrong-type row — green; needs one omission fixture per required field, not one per collection. **A rules type-guard shaped `X is string && X.size() <= N` needs a LIST fixture for its "non-string" case, not a scalar** — `.size()` on a number/bool throws its own eval error and denies anyway, masking whether `is string` fired. Live-verified (BIN-1134 `displayName` create, BIN-1140 `isValidGroupDoc().name`): both `42`-fixtured, both survived; sibling `bio` used `bio: []` and killed it. **A NEWLY ADDED `hasOnly()` allowlist is bound to production only when the CLIENT payload's KEY SET is pinned somewhere**: `toMatchObject({ newField })` is a SUBSET matcher — green when a sibling key is added or renamed — and the rules suite's hand-typed fixtures cannot see the client at all, so a one-word rename of the timestamp key denies EVERY write of that collection in prod at full green (BIN-1063 steg 2, `friends`/`friendRequestsSent`). Ask for `expect(Object.keys(call[1]).sort()).toEqual([...])` per write site (red-alone at each), or the BIN-655 shape named in `vitest.rules.config.ts`'s own comment. **SCOPE THE ASK BY THE RULE, not by the collection's neighbours** — a sibling with no `hasOnly` needs no key-set pin, but that verdict expires the instant the rule starts pinning the set (`friendRequests`/BIN-1106): [arkiv 66, 87, 102]. **An UPDATE-branch type guard on a field only SOMETIMES touched must condition on `field in ...affectedKeys()`, never the whole merged doc** — unconditional denies healing an unrelated field on a row already bad in the guarded one; two mutants (guard deleted vs. conditional stripped) must each name a DIFFERENT test (BIN-1175 sessions `candidates`/`status`).
- No-public-read proof: flip the owner's `isPublic` to true mid-test and re-assert the deny (BIN-164). A flipped `assertFails`→`assertSucceeds` is legit when the rule genuinely split, traced against the new rule text. **GDPR export/deletion must never depend on LIST permission for own-doc access** (BIN-184).
- **A denormalized per-item field can go stale vs its profile source of truth** when the cascade write stamping it dies partway. With a per-item override (BIN-595), pin only that the profile gate can NARROW access. **Firestore subcollections SURVIVE parent-doc deletion** — seed and assert every one (BIN-347). `collectionGroup` queries need an explicit path-shape scope guard.
- No rules-test update is owed when `git status` shows no `firestore.rules` change and a grep of the changed collection against the rules diff shows zero overlap. **A create-only doc-id shape guard mirrored onto a SECOND collection** forces a mass rename of every fixture built from the old bare-numeric id — audit as a potential weakening, not a free pass: [arkiv 39, full BIN-766 trace]. **A hand-copied `hasOnly()`/subtree-roster list replaced by one DERIVED via a brace-walk needs a non-inert floor before any comparison, and the walk BOUNDED to its own `match` block** — unbounded, it silently borrows a LATER block's list when the clause is deleted. [arkiv 102].

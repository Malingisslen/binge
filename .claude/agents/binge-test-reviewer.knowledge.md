## Review protocol & scope discipline
- **Never weaken to go green** — strict→loose, deleted assertion, `.skip`/`.only`, an expectation rewritten to match buggy output: prod code is the suspect. **Pin derived state** (`watchStatus`, `libraryView`, `calendar/summary`, `airingState`, `migrateStatus`). A rules change with no `vitest.rules.config.ts` update (emulator, Java/JBR on PATH) is a gap; `src/lib/design/consistency.test.ts` is never disabled for a lazy change. **A handler→orchestrator split (`index.ts` shrinks to a Firestore/Auth PORT, a new admin-free sibling gets the emulator test) earns a pass only when four things are separately mutation-checked, not read off the file list**: (1) delete a whole sweep/branch and require the failure to NAME the field it broke, not just redden generically; (2) flip any documented `-1`-scan-died-vs-`0`-checked-clean sentinel and require its own dedicated test to catch it; (3) if a safety ceiling is applied at TWO independent call sites (e.g. an auth-delete cap and a separate release/write cap sharing one predicate), break each site ALONE and require the OTHER site's test to stay green — proves the paths aren't one fixture covering both; (4) make a failed batch-commit still increment the "deleted" counter and require a dedicated test for it. BIN-727 (2026-08-15, `retentionCleanup`) is the reference case: all four passed red-alone against `runCleanup.ts`, and all 7 named sweeps were confirmed both seeded AND individually asserted-on (cross-check the sweep count against the extracted file's own docstring inventory) — pass, 0 blocking, full method in the archive entry. **Asserting a raw CSS/Tailwind class string is normally implementation-testing, but it is the RIGHT call when the class IS the fix and jsdom cannot compute the effect** — BIN-660's `toContain('focus-visible:[outline-offset:-2px]')` is the only pin on a ring the card's `overflow:hidden` would otherwise clip away. Having accepted one, check the file's OTHER load-bearing classes the same way — **one probe PER TERM, and a term is not covered by a probe on a NEIGHBOURING term**. Two shapes, both worked live on BIN-660's EventCard: (a) a template-literal className — `` `ev${isTonight?' is-tonight':''}${watched?' is-watched':''}` `` needs a probe for each of the three, since blanking the whole string is 1/N red while dropping `is-watched` ALONE stayed green until an `expect(container.firstElementChild).toHaveClass('is-watched')` was added to the watched case (now 1/12 red alone); (b) **a MODIFIER class does not pin the BASE class it modifies** — `toContain('flex-1')` + `toContain('flex-col')` on `className="flex flex-1 flex-col …"` both pass with the bare `flex` deleted (verified 12/12 green, 2026-08-03), leaving `flex-col` inert; use `classList.contains('flex')` for the base. Same family: inline `style` numbers (`.body`'s `showToggle ? {paddingBottom:8}` gate, the footer's `padding:'0 12px 12px'`) need `toHaveStyle` on the applying case AND `not.toHaveStyle` on the non-applying one — the pair is what kills both "delete the style" (1/12) and "drop the gate" (1/12). File remaining unpinned terms as LOW consistency gaps, not blockers, naming each term rather than the class as a whole.
- Read `.claude/rules/accepted-deviations.md` before filing — the pattern may be a decided call. **Absent a formal accepted-deviation entry, an untested imperative call site (an `if (result === SIGNAL) break` in a firebase-admin-importing loop, untestable under the root toolchain) can still be judged against codebase PRECEDENT rather than filed as a fresh gap**: grep the SAME file/loop for an equivalent-risk SIBLING signal that has shipped untested for a while with no incident — BIN-856 (2026-08-11) added `REQUEST_REJECTED` handling (`if (result === REQUEST_REJECTED) break`) to `streamingOffersRefresh`'s run loop right beside the pre-existing `RATE_LIMITED` break, and a repo-wide grep confirmed the RATE_LIMITED break has NEVER had a test (no unit test, no rules/emulator test) despite being the same shape and same stakes — the pure discrimination (`classifyStatus`) is thoroughly unit-tested and mutation-verified, only the one-line "does the loop actually branch on it" wiring is not, matching this codebase's established test-extraction split (pure logic in an admin-free sibling module, tested; the `onSchedule` handler that calls it, not). Report as informational precedent-consistent, not a blocking gap, and name the sibling signal that sets the precedent — don't demand new extraction (e.g. a `shouldStopBatch` helper) unless the sibling case is ALSO being fixed in the same diff. **The same precedent extends to a DUPLICATED wiring shape, not only a sibling one-liner** — BIN-856 part 2 (2026-08-12, same file) split the pre-existing single `if ((health.status==='warn'||'critical') && prev?.status!==health.status) notifyAdmin(...)` transition guard into two symmetric branches (`capacityStatus`/`feedStatus`, each with its own `notifyAdminFeedDown`), both equally untestable under the root toolchain (index.ts imports firebase-admin) and equally uncovered — but the diff's own `git diff` shows the new branch is a mechanical copy of the untested guard shape that was ALREADY shipping in this exact file, so it inherits the same precedent rather than opening a fresh one. Also worth the technique for judging whether a signature-widening test update (an existing pure-function test file updated to pass a new required argument, here `computeHealth(..., delivery)`) was weakened: mutate the NEW composing step (`worstStatus` picking the lesser instead of the worse) rather than only the new function's own dedicated tests, and check whether the PRE-EXISTING boundary tests (capacity-only, `delivery` held at a neutral "healthy" value) also redden — if they do, that's live proof the old assertions still flow through the new composition and weren't just backfilled with a no-op value to keep them compiling (verified live: the lesser-of mutant failed both the two new `worstStatus`/feed-specific tests AND four pre-existing capacity-boundary tests, e.g. "critical past 62 days"). **A comment-only fix that replaces a retracted claim with a new causal chain needs the chain walked through the actual files it names, and an asymmetry it describes needs BOTH directions checked separately for which is pinned.** BIN-879 (2026-08-15) struck `deletionMarker.test.ts`'s "and the server sweep catches it" clause and replaced it with "a false `false` lets a write through → `ensureUserProfile` recreates `users/{uid}` → the account leaves the sweep's candidate set permanently" — verified true by reading all three hops (`userDocWrite.ts`'s `assertProfileWritable`/`mergePublicProfileDoc` call `isDeletionStarted`; `AuthContext.tsx`'s `ensureUserProfile` returns early only when it reads `true`; `runCleanup.ts` derives `profileMissing` from a live `getAll` of `users/{uid}`, so a recreated doc drops the uid out of the query). The comment sits on a test asserting "throw → false", which mutation-verifies red-alone (1/8, `catch { return true }`) — but that only pins the DANGEROUS direction never firing (a false `true` would wrongly block a live user's writes, separately pinned in `userDocWrite.test.ts`'s `assertProfileWritable`/`mergePublicProfileDoc` throw/resolve-false cases). The BENIGN direction's new consequence — permanent candidate-set loss — is prose-only: no test drives the three-hop chain, and it can't practically be one under this repo's admin-free-vs-admin split (`runCleanup.ts` imports firebase-admin). Before filing that as a gap, check `accepted-deviations.md`: here it's word-for-word the 2026-08-15 "cross-device gap is accepted" entry, so it's informational (say plainly which half is prose-only) rather than a new finding — the corrected comment didn't introduce the gap, it just stopped lying about who closes it.
- Verify, never inherit, claims: "already mutation-tested", a prior entry's numbers, a comment's "would fail against the old code", a marker promising "N notes below" (a promised-but-unwritten finding is itself a defect), and a COORDINATOR's "I mutation-checked two of these myself" — re-run them. **A handed-down "red-ALONE, 1 of N" can be an UNDER-count, and the extra red is worth reading rather than shrugging at**: BIN-816 r4's author reported the marker-re-read mutant (`setDeletionInProgress(deleting || isDeletionStarted(uid))` → `(deleting)`) as 1/66; it is 2/66, because the sibling interleaving test's own PRECONDITION assertion (`expect(ctx!.deletionInProgress, 'förutsättningen: flaggan är uppe').toBe(true)`) fails too. That is the good failure mode — a precondition that reddens instead of silently making the behavioural assertion vacuous — so confirm WHICH assertion each extra red lands on: a precondition firing means the test cannot pass by not reaching its subject. **A handed-down SUITE COUNT ("full suite 2743 passed / 4 skipped") is a claim about the SPEAKER'S machine, not this checkout — run it yourself before believing it, because a test can be coupled to a GITIGNORED build artifact and be green in CI and red on any dev box.** BIN-823 (2026-08-08): `titleParams.watchdog.test.ts` drives the real `generateStaticParams`, which after that diff reads `.tmdb-cache/selection-*.json` through the DEFAULT path (the file never set `TMDB_CACHE_DIR`); with a manifest present the derivation short-circuits, no fetch registers, and 10 of 15 watchdog assertions fail — verified live, and verified as the cause by re-running with `TMDB_CACHE_DIR=$(mktemp -d)` (11 passed). `ci.yml`'s test job restores no such cache, so CI stayed green while the plan's own step 2 ("lokalt dubbelbygge") is what makes it red — the exact setup that invites weakening the test. Standing check on any diff that adds a persisted build artifact: grep the artifact's default-path reader for every test that reaches it and require an explicit temp dir (+ the regime env, here `TMDB_SELECTION_REFRESH=1`) per test file. A test FILE's existence is not coverage: confirm the runner picked it up (`--reporter=verbose`, count the ✓). **And a new test file can REDDEN the suite without any assertion of its own failing** — BIN-816 r2 (2026-08-13) added `src/lib/firebase/accountDeletion.applyPlan.test.ts` to close a mutation gap and thereby broke `docs/org/gen-ownership-map.test.mjs`, which lives INSIDE `npm test`'s own include globs (`docs/org/**/*.{test,spec}.mjs`) and fails 2 tests on `1 NEW unowned sibling(s)`: the file sits in a directory `docs/org/ownership-map.json` lists file-by-file and no role in `docs/role-responsibilities.md` names it, so `node docs/org/gen-ownership-map.mjs --check` exits 1. Verified in the MAIN checkout, not a rig artifact (the sibling `scripts/check-*.test.mjs` RolldownError failures ARE rig-only — they pass in `C:/binge`, so always re-run a suspect failure outside the worktree before calling it environmental). Whenever a diff ADDS a file under an owned directory — a test file counts — run that check yourself before crediting the remediation, or the fix for one blocking finding ships as a new one; the remedy is one line beside the sibling paths under the owning role plus a regenerate. **A SOURCE-SCANNING guard test (`userDocWrite.chokepoint.test.ts`, `src/lib/design/consistency.test.ts`) owes one probe PER IDIOM, and its docstring's absolutes are the claim to attack**: BIN-816's whitelist-over-the-reference regex `doc\(\s*[\w.]+\s*,\s*['"](users|publicProfiles)['"]\s*,\s*[^,)]*\)` really does catch the two idioms it was widened for — a hoisted `const ref = kit.doc(kit.db,'users',uid)` and `doc(db,'users',getUid())` (the char class excludes only `,` and `)`, so a nested call's parens ride through) — each verified by dropping a throwaway `src/lib/__probe*.ts` in and requiring the offender to be NAMED, and it is now self-pinned (blanking the regex, or narrowing `[\w.]+` back to `\w+`, is red-ALONE on the "every exemption still matches" test). But the two-step `const users = collection(db,'users'); doc(users, uid)` escapes it 4/4 green, so a docstring reading "A new file that so much as names the document fails this test, whatever it then does with it" is false: require a second alternation for the bare 2-arg `collection(...)` form, or soften the sentence — a reviewer who trusts the absolute skips the manual check. **A self-reported gap is a claim too — mutate it.** A comment that UNDERSTATES coverage ("NOT COVERED … deleting the latch leaves every test green", plus a filed ticket) is as much a defect as one that overstates: it licenses deleting a guard that IS pinned (BIN-652/645). Honest-sounding self-criticism buys no credit; run the revert. **A comment justifying why a NEIGHBORING, already-tested surface was deliberately left untouched is not evidence that the NEW element added beside it was tested — check the addition's own coverage independently of whatever restraint argument the comment makes about the other surface.** BIN-877 (2026-08-14) landed the identical mailto contact line in two files under one ticket: `DeletionLimbo.tsx`'s copy got a dedicated test, both of whose assertions verified red-alone by mutation (stripping the `<a href="mailto:...">` reddens 1/9; editing one word — "själva" — out of the pinned intro sentence reddens the SAME test alone while the file's pre-existing weaker substring check, `toContain('kontot finns kvar')`, stayed green, proving the fuller pin isn't a tautology of the sibling test). `DeleteAccountSection.tsx`'s copy shipped with a comment correctly arguing that the section's four LOCKED, legally-approved toast strings must not be rewritten to embed the address — true, and a real constraint — but the comment says nothing about the new `<p>` itself, and no test does either: deleting the whole added block left the file's existing 8 tests fully green (verified live). The restraint argument about the toasts and the coverage question about the addition are two different claims; a comment can be right about the first and silent on the second, and a reviewer who reads the comment's reasoning as reassurance about the diff as a whole will miss that. The doc form of the same defect: a `tasks/*.md` close-out staged IN THE SAME COMMIT as the test that closes it, still reading "Acceptance #1 is UNPINNED — no test exists" / "BIN-703 — EventCard has no test file at all" (BIN-660, 2026-08-03). Grep the staged docs for the gap the diff just closed and require the ticket + doc to move with it, else the next sprint re-files or re-does the work. **Same grep, run over ENV FLAGS, catches a commit that contradicts itself**: BIN-823 r7 staged a `preview.yml` setting `SELECTION_ALLOW_THIN: '1'` while the staged ADR 0018 and `.claude/rules/deployment.md` in the SAME commit still read "sätts BARA i `ci.yml` … `deploy.yml`/`preview.yml` kan aldrig råka få den" — a doc that was true for the previous round's code becomes a lie the moment a workflow moves, and this one understates which builds skip the coverage floor. For every env var / feature flag the staged code sets or reads, `git show :<doc>` and grep the flag's name; the doc half often sits UNSTAGED in the worktree already, which makes it a staging step, not a rewrite. **And a flag invariant stated in prose is TESTABLE, not merely greppable** — BIN-823 r8 landed the shape and it discriminates: `readFileSync(join(process.cwd(), '.github/workflows/deploy.yml'), 'utf8')` then `not.toContain('SELECTION_ALLOW_THIN')` plus a companion `toContain('TMDB_SELECTION_REFRESH')` so the check cannot pass on an unread/renamed/emptied file. Verified: inserting the flag into deploy.yml is red-ALONE 1/30, deleting the companion line is red-ALONE 1/30. Ask for this whenever a safety property reduces to "workflow W must never set flag F" (it had been asserted in FOUR prose sites and checked nowhere). One residual to know and not file WHILE the assertion pins a NAME: `toContain` is prefix-satisfiable (renaming the var to `TMDB_SELECTION_REFRESH_MUTANT` survives 30/30) and file-wide (a comment quoting the fragment satisfies it too) — cosmetic when the realistic regression is the line DISAPPEARING. The moment such an assertion pins a VALUE instead, both residuals become live and the line-anchored `toMatch(/^\s*key:.*<value>\s*$/m)` is the required form (verified r10 — see the cap-margin bullet under Boundary & threshold completeness). **The INVERSE shape is self-certification and shows up as an index sha moving MID-review**: BIN-660's `tasks/todo.md` was re-staged at 08:17 while my mutation loop ran, already reading "code, test and integration reviewers each `pass (0 blocking)` over three rounds, their 11 Low findings all applied" — my verdict, recorded before I issued it. Outcome happened to match, so it is INFORMATIONAL not blocking, but re-pin every sha at the end (a doc mover is still a mover: diff it, re-read the section covering your own surface) and say in the verdict that the doc pre-dated it. Also count the doc's own numbers — the same sentence claimed "9 mutants killed" while listing 11. **A test file's own comment naming TWO mutation classes it claims to guard against is two separate claims, not one — mutate each named class independently.** BIN-844's `groupInviteCache.test.ts` header says the sweep pins "removing inside an index loop" AND "taking keys that merely contain the prefix"; the index-loop claim is real (a live `for(i<length)` removeItem-shift mutant is red-alone), but no fixture in the file ever puts the prefix substring anywhere but position 0, so `k.startsWith(PREFIX)` → `k.includes(PREFIX)` survives 4/4 green (verified live, 2026-08-10) — the second claim is false. LOW (no realistic binge key embeds `binge:groupInvite:` mid-string), but file it rather than wave it through because the sibling claim in the same comment checked out. **CLOSED same day**: a fourth fixture (`store['x-binge:groupInvite:g9'] = 'not-ours'`) with the prefix substring at index 2 instead of 0 now discriminates — re-verified red-alone 1/5 on the live mutant. The general rule the fix demonstrates: a decoy for `startsWith`-vs-`includes` needs the substring NOT AT POSITION 0, not merely present somewhere in the store; a decoy whose match happens to start the string satisfies both operators and proves nothing. **A docstring claiming a composed function is "the only place a reader pairing is proven" only proves the half it happens to exercise.** `scripts/check-public-env.mjs`'s `analyzeWorkflow` composes a STRICT reader (`readVarsFromWorkflow`, requires the exact `NAME: ${{ secrets.NAME }}` backreference) into `unwired` and a LOOSE reader (`readAssignedVars`, any assignment at all) into `missingInline`/`wronglyWired`, with a comment naming this composition as the seam that keeps the two from being silently swapped — but every `analyzeWorkflow`-level fixture in the file has `assigned` and `wired` AGREE for the variable in play (fully wired via a real secret, or fully absent), so swapping `unwired`'s reader to the loose one survives 18/18 (verified live, 2026-08-10): a mis-wired secret (wrong name on one side, or a hardcoded literal) would then read as "wired" through the exact composed function `main()` calls — recreating the incident class the script exists to prevent, through the one path that ships. Require a fixture where the two readers DISAGREE (a variable wired to the WRONG secret name, or as a bare literal, while still present in `sourceVars`) before crediting a "this seam is pinned" comment on a dual-reader composition. Same review, a narrower miss of the identical shape: a comment justifying a regex boundary tightened FROM `\s*\S` TO `[ \t]*\S` ("a wrapped YAML value" would slip through the old form) does not correspond to any real discriminating input once the text is already split per-line (`\S` itself is always whitespace-complement regardless of what precedes it) — the two forms disagree ONLY on exotic non-tab/space whitespace (e.g. a literal NBSP) that never occurs in a real workflow file, so the widened-back mutant is a genuine, low-stakes survivor (0/18, not the claimed 1/18) rather than the described regression; probe the claimed distinguishing input directly (build both regexes, run them over the fixture the comment describes) before accepting that a "boundary" comment is protecting anything live. **A handed-down mutation TALLY can be flatly wrong while the code under test is fine — run the exact described mutation, don't average it against the reported number.** BIN-808 round 2's dispatch message claimed collapsing ten explicit `covers[]` boundary tokens into one `error.tsx` gives "29/31, the new per-token test plus the committed-data test, and the linter itself goes red"; re-run live it is 30/31 (only the new per-token-uniqueness test fails) and `node scripts/check-workflow-map.mjs` stays OK 73/73 — because the collapsed `'error.tsx'` claim still whole-segment-TAIL-matches all ten full paths via `coversEntry`, so `checkCoverage` (and the committed-data test built on it) never notices anything went missing. This is exactly what the new test's OWN comment predicts ("would keep coverage 73/73 green today"), so the test and code are correct and the dispatch message's tally was simply never re-run before being reported. Non-blocking (the guard works, verified independently), but say so in the verdict rather than transcribing the claimed numbers — a plausible-sounding, partially-correct handed-down count is easier to wave through than an obviously wrong one. **A golden-table SELF-CONSISTENCY property test — e.g. "EXACTLY ONE row differs between two intent columns," computed from the table's OWN literal fields and never calling production — reads as self-fulfilling (it only checks that the author typed matching values) but can carry real, independent protective value; verify which by widening prod scope on a SECOND row and ALSO dutifully updating that row's table entry to match the new (wrong) behaviour, the way a diligent-but-wrong future author would.** BIN-655's `buildAddWrite` parity matrix (2026-08-14): with a second row's `viewing` column edited to match a genuine scope-creep mutation (an unrelated re-mark now also re-dates on intent), every per-row `it.each` — which DOES call the real function — stays green (the author's own expectation now matches the mutant), and the property test is the ONLY thing that catches it, red-alone (1/50, `differing` lists two names instead of the pinned one). That is the exact failure a naive per-row equality suite cannot see: code and table drifting together, keystroke for keystroke. Demand this check whenever a parity/golden table claims "only one row/cell may ever differ" as its documented contract, and verify it with this two-part mutation (widen + relabel), not merely by reading the table once. **A comment claiming cross-file string coupling ("rewrite the message over there and this test goes red") is disprovable on its face the moment the SAME comment, two sentences earlier, says the boundary is wholly mocked — a mock means nothing on the other side of it can EVER reach this test, rewritten or not.** BIN-813 (2026-08-15): `DeletionLimbo.test.tsx`'s new sequence test says, honestly, that `useAuth` is mocked wholesale so `deleteAccount` is a bare `vi.fn` and the pre-check's error-code CHOICE "can omöjligt prövas härifrån" — true, verified (no route exists without duplicating `AuthContext.test.tsx`'s entire Firebase mock rig, which belongs in that file's scope, not this component test's) — then two sentences later claims the test is "ordagrant strängen AuthContext.tsx numera kastar, så en omskrivning där utan en ändring här blir rött" (verbatim the string AuthContext.tsx now throws, so rewording it there without updating here goes red), repeated a second time inline before the second `mockRejectedValueOnce`. Both are false, and self-contradicting given the sentence right before them: the test hardcodes its own `new Error(...)` literal and never imports or executes `AuthContext.tsx` at all (that's what "mocked wholesale" means), so rewording the production string — verified live, `sed`-editing the exact production message to unrelated text while leaving the test untouched — leaves all 10 `DeletionLimbo.test.tsx` tests green, including the one making the claim. The two files' literal strings are coupled only by a human remembering to update both; nothing mechanical enforces it, in either direction (`AuthContext.test.tsx` never reads `DeletionLimbo.test.tsx`'s hardcoded copy either). Whenever a test-file comment claims a coupling to a mocked-away module's literal output, mutate the SOURCE file's wording (not just its token/branch content) while leaving the mocking test untouched and confirm it actually reddens before crediting the "coupling" claim — a claim can be accurate about non-testability one sentence and overclaim a coupling that mocking specifically forecloses the next. The rest of that same comment (the classifier-tightened-to-require-STALE_SESSION_PREFLIGHT mutant "fells the Firebase-format test below it too, so this isn't a unique kill") measured true: live-mutated `classifyDeletionFailure`'s `recent-login` branch to also require `STALE_SESSION_PREFLIGHT` present, exactly 2 failed (the new BIN-813 test and "Firebases eget recent-login-fel hamnar i samma gren"), matching the comment's own count — an honest self-graded non-uniqueness claim beside a false coupling claim in the same paragraph, so grade each sentence of a self-critical comment separately rather than accepting or rejecting the whole block on one verified/falsified line. On the file's THREE `AuthContext.test.tsx` tests for the same ticket: forcing the marker read `false &&` (as if always unmarked) kills exactly the "marker down" test (1/69) and leaves the dedicated unmarked-control test green (it already exercises the unmarked path); forcing it `true ||` (as if always marked) kills the control test PLUS three pre-existing siblings that assume unmarked behaviour (4/69) — the control fires in exactly the direction that proves it isn't decorative, the textbook shape for "a control that never reddens is not a control."
- **FIRST command of every review**: loop `git rev-parse :<f>` vs `git hash-object <f>` over `git diff --cached --name-only`, and **PRINT the sha for EVERY path, not only the mismatches** — a mid-review mover that a sibling session STAGES advances index and worktree together, so it is completely silent under a mismatch-only loop (BIN-823 r10: `.claude/rules/deployment.md` `1b4fd6e→e5a5c85` was caught only because the END-of-review re-pin printed the full list; the file's content had visibly changed while the loop said nothing). Any mismatch = split index/worktree; `vitest` reads the WORKTREE, CI the INDEX. Two Critical shapes: (a) a one-line fix's COMMENT staged but not the line — reads as done, ships buggy (BIN-617); (b) a new file shows `A` yet is staged EMPTY via intent-to-add (blob `e69de29…`). Remedy: plain `git add <path>` (never on the coordinator's behalf), re-diff shas. On a genuine split prove impact — swap `git show :path` into the worktree, run, restore, `diff -q`, verdict `APPROVED-WITH-CAVEAT` naming the delta. **Third shape (BIN-641 r4): the FIX is in the worktree, the GAP in the INDEX** — a concurrent session closed the very gap I was proving while `git rev-parse :<f>` still returned the gap-carrying blob. Then: mutation-verify the WORKTREE bytes, pin THEIR `git hash-object` shas, state the index shas separately, name `git add <paths>` as the required step — never run it yourself. Nothing staged ⇒ `:<path>` = the HEAD blob; pin on `git hash-object`. On a RE-review, `git diff <old-sha> <new-sha>` per file. **Fourth shape — the INDEX IS EMPTIED mid-review by a sibling session's unrelated commit** (BIN-679, 2026-08-08: three foreign commits landed, `git diff --cached` went empty, every reviewed file fell back to ` M` and the batch's NEW test file back to `??` untracked). The worktree blobs still hashed as reviewed, so the review stands — but say so and make re-staging a BLOCKING step, naming every path incl. the untracked test: an untracked test file plus a `git commit -a` ships the production guard with no test at all, and that is the BIN-707/708 evaporation class arriving through git rather than through a sprint. **RECURRED 2026-08-11 (BIN-849 round 2) via a narrower mechanism — no foreign commit emptied the whole diff, one sibling-session action reshaped the index selectively**: mid-mutation-run, `git diff --cached --name-status` still showed the 5 reviewed files, but a plain `git status --porcelain` re-check right after showed `src/lib/firebase/messaging.livetoken.test.ts` demoted from staged `A` to untracked `??`, while THREE files from an unrelated ticket (`functions/src/streamingOffers/motn.ts`/`motnUrl.ts`/`motnUrl.test.ts`) had newly appeared staged — `HEAD` had also moved (a sibling's own commit landed in between). Worktree bytes for the demoted test file still hashed identical to the originally-staged blob, so the CONTENT review stood — but committing at that moment would have shipped `messaging.ts`'s new function with ZERO test file (untracked ⇒ excluded) while silently bundling an unreviewed production change from a different ticket. Same remedy, sharper trigger: a file transitioning out of the index is detectable ONLY by re-running plain `git status --porcelain` (not `--cached --name-status`, which reads the index directly and looked fine) at the end, and the fix is always "name it as the required `git add`, never run it yourself." Re-run `git status --porcelain` + `git log --oneline -1` at the END of every review, not just the start; a moved HEAD also means a sibling session is live in the checkout, so re-hash every mutation target before writing the verdict. **Fifth shape — the INDEX holds still and the WORKTREE moves under you, carrying NEW production logic** (BIN-823 r3, 2026-08-08: all 23 staged blobs matched at the first check; at the final check 8 had diverged, and the unstaged delta included `SEO_PERSON_TARGET_IDS 1000→800`, a new `it.each` block and a moved `class SelectionFloorError`). ## Mutation-testing protocol (the house method)
- Per criterion: edit the REAL prod file → run → confirm the expected AND ONLY the expected test fails → restore from a scratchpad backup (`diff -q` it byte-identical) → `git diff` shows only the real work → suite green → next. Never `git stash` mid-review (unstages staged files); never `git checkout --` a file that may hold other uncommitted work. **After restoring, re-check the INDEX, not just the worktree** — this checkout has something (a hook, a sibling session, a save-watcher) that auto-`git add`s a saved file, so a mutation edit can transiently land IN THE INDEX even though the worktree restore is byte-identical to backup. Caught live (BIN-844, 2026-08-10): `git hash-object` on the restored worktree matched the pre-mutation sha, but `git rev-parse :<f>` had moved to a DIFFERENT sha than either the mutation or the original — the staged bytes briefly carried the mutant. `git status --porcelain <f>` showing `MM` (not clean `M `) right after a restore is the tell; `git add <f>` again and re-diff `git diff --cached` against the pre-mutation content before trusting the index for the verdict. **`git hash-object` vs `git rev-parse :<f>` is the FIRST command, before touching anything, precisely because a file can ALREADY be sitting mutated in the worktree at the moment a review starts — a leftover, un-restored mutation from a crashed prior session or another agent's tool use, not this review's own edit.** BIN-848 r3 (2026-08-10): the very first `Read` of `logic.ts` showed a live `// MUTANT: guard removed` comment with the try/catch already stripped, and `git hash-object` vs `git rev-parse :<f>` disagreed before any Edit was made. ## Vacuous / non-discriminating oracles
- **A TRANSIENT render state is invisible to any oracle read at the end, and a single `await act()` collapses it** — the mutant that matters is a flag flipped ON at the start of an async run and OFF again at the end (BIN-816: `setDeletionInProgress(true)` placed beside `markDeletionStarted`, which swaps the whole app for the limbo screen for the tens of seconds a heavy account's cascade takes, on the HAPPY path). A per-render recorder (`const flagRenders: boolean[] = []` pushed from the harness component's body, cleared in `beforeEach` AND again inside the test after any sign-in helper) is necessary but not sufficient: inside ONE `act()` React batches the whole run into a single commit and the intermediate `true` never reaches a render, so the mutant survives (it did, twice, before the shape below). Drive it as **hold → observe → release**: mock the first awaited collaborator to return a promise you control, `await act(async () => { pending = fn(); })`, assert `flagRenders` `.not.toContain(true)` there, then `await act(async () => { release(); await pending; })` and assert again. Once `disabled={authLoading}` lands, BOTH in-handler auth guards (`signedOut`'s `!authLoading` and `handleRemove`'s copy) are unreachable — don't call either load-bearing, and don't file the green mutation; see the disabled-button rule. **"Exact string, `.search` included" must be checked PER SIBLING, not once per pattern**: BIN-668 copied the same `rememberNextPath(window.location.pathname + window.location.search)` handler into TopbarActions AND HomePageClient's landing CTA, but only TopbarActions' fixture set a query (`/search?q=dune`) — HomePageClient's fixture stayed on bare `/`, so dropping `+ window.location.search` there passed 8/8 green (verified live). Low severity only because the home route never carries a meaningful query today; flag it, don't block on it, and re-check the moment `/` grows a query-driven view state.
- **Mocking the provider hooks pins the COMPONENT and leaves the PROVIDER's state machine unasserted** — `vi.mock('@/hooks/useWatchlist')` full-replacement is fine for exactly that scope, no more. Mutate the provider facts the component tests assume: `useState(true)` for `loading` → `false`, and any "deliberately stays true" branch (BIN-601's onSnapshot error handler) → `setLoading(false)`; both left 49 green. Owed: `loading` assertions in the file rendering the REAL provider — true before the first snapshot, false after, false for a null uid, still true after an error callback. **A DERIVED boolean the provider exposes (`libraryKnown = snapshotSettled && !listenerFailed`) must be mocked as a GETTER computed from the same two primitives, never a settable literal** — a literal lets a test set `listenerFailed: true` and still hand the component `libraryKnown: true`, a combination production cannot produce, silently voiding every gate assertion in the file (BIN-596's CollectionSection/QuickAddButton mocks both do this correctly: `get libraryKnown(): boolean { return this.snapshotSettled && !this.listenerFailed; }`, byte-identical to `WatchlistContext.tsx`'s own derivation — grep-diff the two formulas, don't just eyeball them). Being getter-only also makes an accidental `watchlist.libraryKnown = true` in a test throw (strict-mode ES modules) rather than silently no-op. Confirm reachability, not just the formula match: check each of the 4 boolean combinations is independently producible by the real onSnapshot success/error callbacks — the easy-to-miss cell is "listener fails before ever settling" (`snapshotSettled: false, listenerFailed: true`), reachable when the FIRST snapshot attempt errors. Verified live 2026-08-04 on CollectionSection.test.tsx: comprehensively reverting every `mounted && libraryKnown` gate to bare `mounted` in the production file fails 3 of its 5 dedicated tests alone (not the 2 a prior report claimed — always re-run the count rather than inheriting it, even when the direction is "more covered than claimed").
- **Two exceptions override the exemption above:** (1) the ticket lists a test as an acceptance criterion — an unmet self-imposed bar is a gap even in an exempt shape; extracting the buried decision (BIN-599 → BIN-611's `planQuickRateWrite`) is only HALF the remedy, since the helper's verdict is inert until the CALLER is pinned obeying it. (2) the gate protects a counter/date the code calls permanent-and-uneditable (`rewatchCount`, `watchedAt`) — earns a test at one-boolean size; reserve the exemption for gates whose failure is a redundant render, not silent corruption.

## Rounding, jsdom, TZ/DST
- Rounding oracles need `.5`-exact fixtures (`79/2=39.5`: round=40 vs floor=39) (BIN-87); `Math.round(x*2)/2` with only an `x>0` guard snaps 0.25 to 0 — probe `0.1`. jsdom `getBoundingClientRect()` is always a zero DOMRect. **A "both directions plus the inclusive boundary" claim about a strict inequality (`a > b`) names TWO DIFFERENT mutants, not one — verify each separately.** Reversing the operator (`>`→`<`) tests DIRECTION and is silent exactly AT equality (neither `a>b` nor `a<b` fires when `a===b`), so it cannot be what pins an "boundary is inclusive" fixture; only widening it to include equality (`>`→`>=`) does. BIN-918's `check_events.mjs` freshness gate (`commitDate > row.ts` ⇒ violation) is the clean worked example: `>`→`<` reddens the two directional fixtures (`FAILS…NEWER`, `PASSES…already existed`) plus three collateral tests, but leaves `PASSES a commit stamped at exactly the row time — the boundary is inclusive` GREEN; only `>`→`>=` reddens that one, red-alone. Both mutants are realistic (an author fixing a reported off-by-one is exactly as likely to loosen `>` to `>=` as to reverse it), so both are owed — but "flip the operator" as an instruction is ambiguous between them, and a reviewer who runs only the direction-flip and finds the boundary fixture unreddened by it should try `>=`/`<=` before concluding the boundary claim is unpinned.
- **`fireEvent.click` on a `disabled` button fires NO handler**, so adding `disabled={cond}` RETROACTIVELY hollows out an existing case's post-click assertions: a mutation that used to go red goes green. Verified twice (BIN-645). So on any diff adding `disabled`/`aria-disabled`, RE-RUN the prior round's handler mutations rather than carrying the verdict. Usually NOT a gap: the in-handler guards become unreachable behind an attribute the same case pins (`toBeDisabled()` goes red if removed) — accepted defense-in-depth — but the comments must stop claiming to prove handler behaviour.
- A DST guard is real only if the buggy fixed-ms path yields a DIFFERENT calendar date at that fixture — spring-forward never crosses local midnight (tautologically green), so anchor across FALL-BACK (Sun 2026-10-25) and assert the exact ISO under `TZ=Europe/Stockholm`. Floor BOTH sides to local midnight for whole-day diffs (BIN-145); pick an instant where zones disagree (23:30 UTC = next day CEST) (BIN-105/350).

## Parsers, regex, dispatch, lookup tables & SEO
- `\d+` parsers: test the syntactically-valid-but-semantically-invalid boundary (`/movie/0` → null); strict-digit hardening needs empty-string and phantom-id-0 cases (BIN-560). Regex tightening: a NEGATIVE + POSITIVE pair per pattern — negative-only passes even if the regex reverts (BIN-176); anti-over-rejection tests are as load-bearing as the reject side. `\b` after a hyphenated token false-matches `accent-soft` — use lookarounds. **A "requires a non-empty value" character class (`\S` right after a delimiter) is its own boundary and needs a BARE-KEY fixture, not just a different-value fixture** — `check-public-env.mjs`'s `readAssignedVars` matches `/^\s*(NAME):\s*\S/` specifically so a bare `NEXT_PUBLIC_X:` (no value, YAML-null) doesn't count as "assigned"; every fixture in the file gives the key SOME value (`'true'`, `${{ secrets.X }}`), so dropping the trailing `\S` survives 14/14 (verified live, 2026-08-10). Narrow/LOW when the bare form is an unrealistic paste, but ask for the fixture whenever a "present vs blank" regex ships a `\S`/`\S+` tail.
- Ordered dispatch: the ordering test uses a path matching an early branch correctly and a later one incorrectly (BIN-345). `as Record<string, any>` trips CI's `no-explicit-any` — cast the narrowest slice; `npx eslint` new test files (warnings OK, errors block).
- Alias tables: one exhaustive identity loop (every entry × every alias) covers current AND future aliases (BIN-64/90). An ALLOWLIST needs a fixture per MEMBER, not just per rejected value: BIN-645's `RETURN_QUERY_KEYS` was reject-side pinned (adding `'invite'` → red) yet DELETING `'row'` left 25/25 green while killing that surface's return path. Name every member in the keeps-it case; one added `expect` makes the deletion red-alone — re-derive PER MEMBER, not once (`q` reddens 2 cases, `status`/`provider`/`row` 1 each).
- **A URL/route fixture is a factual claim: grep it back to the line that BUILDS it.** Plausible-looking invented routes recurred EIGHT times across BIN-640/645, once inside the fix for the previous one. Check three things per fixture — the route directory exists under `src/app/`, the query KEY is read by that page, and the query VALUE is one the app can actually produce: `/rekommendationer/?row=2` was wrong on all three (`RecRow.tsx` builds `` `/recommendations/?row=${encodeURIComponent(rowSpec.rowKey)}` `` and `rowKey(id)` is colon-joined, so `?row=person%3A1245`), and `/my/all?status=sedd` was wrong on two (`NumberedActionsList` builds `/my/series?provider=N&status=behind`; `WatchlistPage` only honours `?status=` when `status==='mina'`, i.e. `/my/series`). A fixture that names a surface the app never had keeps passing after that surface moves, so it pins nothing. Curated domain id lists get cross-checked against external ground truth AND the enums/label maps they derive from. Sitemap: two-sided enumeration with REAL constants + an auth/noindex-leak scan (BIN-337/305). **Same discipline for a rejected-Error fixture feeding a message-sniffing branch (`err.message.includes(CODE)`): grep the fixture's string back to the line that actually THROWS it, not to the constant's declaration alone.** BIN-777's `DeleteAccountSection.test.tsx` first shipped `new Error(STALE_SESSION_PREFLIGHT)` — just the bare code — when the real thrower (`AuthContext.tsx:991`, `` throw new Error(`${REQUIRES_RECENT_LOGIN} (${STALE_SESSION_PREFLIGHT}): …`) ``) puts BOTH codes in one message on purpose, specifically so a caller sniffing in the wrong order can't tell them apart. A fixture with only the narrow code is reachable under EITHER branch order, so the swap mutant (check `REQUIRES_RECENT_LOGIN` before `STALE_SESSION_PREFLIGHT`) survived 5/5 — closed by rebuilding the fixture as the literal template string the thrower emits (verified live: swap mutant now fails 1/5 alone). Two sibling messages sharing an identical PREFIX (here, a promise-bearing sentence appended only on one branch) additionally want the differing suffix asserted on its own (`toContain` the promise clause / `not.toContain` it) so a prefix-preserving swap can't hide behind the shared substring.

## Review protocol & scope discipline
- **Never weaken to go green** — strict→loose, deleted assertion, `.skip`/`.only`, an expectation rewritten to match buggy output: prod code is the suspect. **Pin derived state** (`watchStatus`, `libraryView`, `calendar/summary`, `airingState`, `migrateStatus`). A rules change with no `vitest.rules.config.ts` update (emulator, Java/JBR on PATH) is a gap; `src/lib/design/consistency.test.ts` is never disabled for a lazy change. **Asserting a raw CSS/Tailwind class string is normally implementation-testing, but it is the RIGHT call when the class IS the fix and jsdom cannot compute the effect** — BIN-660's `toContain('focus-visible:[outline-offset:-2px]')` is the only pin on a ring the card's `overflow:hidden` would otherwise clip away. Having accepted one, check the file's OTHER load-bearing classes the same way — **one probe PER TERM, and a term is not covered by a probe on a NEIGHBOURING term**. Two shapes, both worked live on BIN-660's EventCard: (a) a template-literal className — `` `ev${isTonight?' is-tonight':''}${watched?' is-watched':''}` `` needs a probe for each of the three, since blanking the whole string is 1/N red while dropping `is-watched` ALONE stayed green until an `expect(container.firstElementChild).toHaveClass('is-watched')` was added to the watched case (now 1/12 red alone); (b) **a MODIFIER class does not pin the BASE class it modifies** — `toContain('flex-1')` + `toContain('flex-col')` on `className="flex flex-1 flex-col …"` both pass with the bare `flex` deleted (verified 12/12 green, 2026-08-03), leaving `flex-col` inert; use `classList.contains('flex')` for the base. Same family: inline `style` numbers (`.body`'s `showToggle ? {paddingBottom:8}` gate, the footer's `padding:'0 12px 12px'`) need `toHaveStyle` on the applying case AND `not.toHaveStyle` on the non-applying one — the pair is what kills both "delete the style" (1/12) and "drop the gate" (1/12). File remaining unpinned terms as LOW consistency gaps, not blockers, naming each term rather than the class as a whole.
- Read `.claude/rules/accepted-deviations.md` before filing — the pattern may be a decided call.
- Verify, never inherit, claims: "already mutation-tested", a prior entry's numbers, a comment's "would fail against the old code", a marker promising "N notes below" (a promised-but-unwritten finding is itself a defect), and a COORDINATOR's "I mutation-checked two of these myself" — re-run them. **A handed-down SUITE COUNT ("full suite 2743 passed / 4 skipped") is a claim about the SPEAKER'S machine, not this checkout — run it yourself before believing it, because a test can be coupled to a GITIGNORED build artifact and be green in CI and red on any dev box.** BIN-823 (2026-08-08): `titleParams.watchdog.test.ts` drives the real `generateStaticParams`, which after that diff reads `.tmdb-cache/selection-*.json` through the DEFAULT path (the file never set `TMDB_CACHE_DIR`); with a manifest present the derivation short-circuits, no fetch registers, and 10 of 15 watchdog assertions fail — verified live, and verified as the cause by re-running with `TMDB_CACHE_DIR=$(mktemp -d)` (11 passed). `ci.yml`'s test job restores no such cache, so CI stayed green while the plan's own step 2 ("lokalt dubbelbygge") is what makes it red — the exact setup that invites weakening the test. Standing check on any diff that adds a persisted build artifact: grep the artifact's default-path reader for every test that reaches it and require an explicit temp dir (+ the regime env, here `TMDB_SELECTION_REFRESH=1`) per test file. A test FILE's existence is not coverage: confirm the runner picked it up (`--reporter=verbose`, count the ✓). **A self-reported gap is a claim too — mutate it.** A comment that UNDERSTATES coverage ("NOT COVERED … deleting the latch leaves every test green", plus a filed ticket) is as much a defect as one that overstates: it licenses deleting a guard that IS pinned (BIN-652/645). Honest-sounding self-criticism buys no credit; run the revert. The doc form of the same defect: a `tasks/*.md` close-out staged IN THE SAME COMMIT as the test that closes it, still reading "Acceptance #1 is UNPINNED — no test exists" / "BIN-703 — EventCard has no test file at all" (BIN-660, 2026-08-03). Grep the staged docs for the gap the diff just closed and require the ticket + doc to move with it, else the next sprint re-files or re-does the work. **Same grep, run over ENV FLAGS, catches a commit that contradicts itself**: BIN-823 r7 staged a `preview.yml` setting `SELECTION_ALLOW_THIN: '1'` while the staged ADR 0018 and `.claude/rules/deployment.md` in the SAME commit still read "sätts BARA i `ci.yml` … `deploy.yml`/`preview.yml` kan aldrig råka få den" — a doc that was true for the previous round's code becomes a lie the moment a workflow moves, and this one understates which builds skip the coverage floor. For every env var / feature flag the staged code sets or reads, `git show :<doc>` and grep the flag's name; the doc half often sits UNSTAGED in the worktree already, which makes it a staging step, not a rewrite. **And a flag invariant stated in prose is TESTABLE, not merely greppable** — BIN-823 r8 landed the shape and it discriminates: `readFileSync(join(process.cwd(), '.github/workflows/deploy.yml'), 'utf8')` then `not.toContain('SELECTION_ALLOW_THIN')` plus a companion `toContain('TMDB_SELECTION_REFRESH')` so the check cannot pass on an unread/renamed/emptied file. Verified: inserting the flag into deploy.yml is red-ALONE 1/30, deleting the companion line is red-ALONE 1/30. Ask for this whenever a safety property reduces to "workflow W must never set flag F" (it had been asserted in FOUR prose sites and checked nowhere). One residual to know and not file WHILE the assertion pins a NAME: `toContain` is prefix-satisfiable (renaming the var to `TMDB_SELECTION_REFRESH_MUTANT` survives 30/30) and file-wide (a comment quoting the fragment satisfies it too) — cosmetic when the realistic regression is the line DISAPPEARING. The moment such an assertion pins a VALUE instead, both residuals become live and the line-anchored `toMatch(/^\s*key:.*<value>\s*$/m)` is the required form (verified r10 — see the cap-margin bullet under Boundary & threshold completeness). **The INVERSE shape is self-certification and shows up as an index sha moving MID-review**: BIN-660's `tasks/todo.md` was re-staged at 08:17 while my mutation loop ran, already reading "code, test and integration reviewers each `pass (0 blocking)` over three rounds, their 11 Low findings all applied" — my verdict, recorded before I issued it. Outcome happened to match, so it is INFORMATIONAL not blocking, but re-pin every sha at the end (a doc mover is still a mover: diff it, re-read the section covering your own surface) and say in the verdict that the doc pre-dated it. Also count the doc's own numbers — the same sentence claimed "9 mutants killed" while listing 11.
- **FIRST command of every review**: loop `git rev-parse :<f>` vs `git hash-object <f>` over `git diff --cached --name-only`, and **PRINT the sha for EVERY path, not only the mismatches** — a mid-review mover that a sibling session STAGES advances index and worktree together, so it is completely silent under a mismatch-only loop (BIN-823 r10: `.claude/rules/deployment.md` `1b4fd6e→e5a5c85` was caught only because the END-of-review re-pin printed the full list; the file's content had visibly changed while the loop said nothing). Any mismatch = split index/worktree; `vitest` reads the WORKTREE, CI the INDEX. Two Critical shapes: (a) a one-line fix's COMMENT staged but not the line — reads as done, ships buggy (BIN-617); (b) a new file shows `A` yet is staged EMPTY via intent-to-add (blob `e69de29…`). Remedy: plain `git add <path>` (never on the coordinator's behalf), re-diff shas. On a genuine split prove impact — swap `git show :path` into the worktree, run, restore, `diff -q`, verdict `APPROVED-WITH-CAVEAT` naming the delta. **Third shape (BIN-641 r4): the FIX is in the worktree, the GAP in the INDEX** — a concurrent session closed the very gap I was proving while `git rev-parse :<f>` still returned the gap-carrying blob. Then: mutation-verify the WORKTREE bytes, pin THEIR `git hash-object` shas, state the index shas separately, name `git add <paths>` as the required step — never run it yourself. Nothing staged ⇒ `:<path>` = the HEAD blob; pin on `git hash-object`. On a RE-review, `git diff <old-sha> <new-sha>` per file. **Fourth shape — the INDEX IS EMPTIED mid-review by a sibling session's unrelated commit** (BIN-679, 2026-08-08: three foreign commits landed, `git diff --cached` went empty, every reviewed file fell back to ` M` and the batch's NEW test file back to `??` untracked). The worktree blobs still hashed as reviewed, so the review stands — but say so and make re-staging a BLOCKING step, naming every path incl. the untracked test: an untracked test file plus a `git commit -a` ships the production guard with no test at all, and that is the BIN-707/708 evaporation class arriving through git rather than through a sprint. Re-run `git status --porcelain` + `git log --oneline -1` at the END of every review, not just the start; a moved HEAD also means a sibling session is live in the checkout, so re-hash every mutation target before writing the verdict. **Fifth shape — the INDEX holds still and the WORKTREE moves under you, carrying NEW production logic** (BIN-823 r3, 2026-08-08: all 23 staged blobs matched at the first check; at the final check 8 had diverged, and the unstaged delta included `SEO_PERSON_TARGET_IDS 1000→800`, a new `it.each` block and a moved `class SelectionFloorError`). Mutating in a worktree built from `git write-tree` means your evidence IS the index, which is what `git diff --cached` commits — so the verdict stands, but say plainly that it is pinned to those blob shas, list every mover, and state that `git add` of any mover puts unreviewed bytes in the commit. A concurrent session fixing a defect you were about to file is the normal cause: check each mover's diff before assuming it is noise, and report which of your findings it already addresses UNSTAGED (still a finding against the reviewed bytes). RECURRED BIN-823 r7 (2026-08-09) with the sharpest version yet: 7 blobs moved during the run and the unstaged delta contained (i) the exact remedy for the gap I had just mutation-verified, (ii) the doc halves that make the staged commit self-consistent, and (iii) BRAND-NEW production behaviour nobody reviewed — `sitemap.ts`'s `if (allowThinSelection()) return [...seedIds]`, which removes the sitemap's build-failing throw on a missing manifest. So the verdict sentence has to be three-part: the index bytes pass, the movers carry fixes worth staging, and `git add` of a mover that touches `src/**` puts UNREVIEWED production code in the same commit — name the file and demand its own pass rather than waving it through because it "closes my finding". Then the sixth shape fired in the same minute: the sibling STAGED all seven while I was writing the verdict, so the index I had pinned no longer existed. **Never write the verdict off a sha list you read before your last edit to the knowledge files** — re-pin, and when the index has absorbed the movers, build a SECOND rig from the new tree and re-run (cheap: the movers are few and the mutation set is known). Here that took one `npm ci` + four runs and CHANGED the verdict's content: the gap I had just filed came back red-alone 1/73 (closed), and the newly-staged `sitemap.ts` guard proved pinned in all three directions (removed → 1 red, `[...seedIds]`→`[]` → 1 red, inverted → 3 red), full suite 2768/4 skipped, zero `::warning::` in the output. A finding that a mover closes is REPORTED as closed-by-mover, never silently dropped.
- **Re-read the shas IMMEDIATELY before writing the marker.** Concurrent sessions share this checkout and the INDEX moves mid-review (BIN-596/617). Never pin a sha you did not finish on: diff each mover, re-run every mutation touching the changed lines against the NEW bytes, pin, and SAY so. Conversely, a sha-pinned marker makes a FOLLOW-UP pass legitimately short: blobs whose sha is unchanged carry their prior verdict, so scope to the movers — but only after diffing each one, and a comment-only mover still owes the decisive mutation against the new bytes plus a fresh reachability grep. "An added test can only turn things RED, so prior green mutations stand" holds ONLY while the test file's harness is untouched — a MOCK edit (hoisting `useRouter` to a stable object, adding a field to a mocked hook, adding `disabled`) rewrites the contract every sibling runs under and can turn a prior RED green, so re-run the file's whole mutation set. A prior marker's WORKTREE-only sha may no longer exist as an object — diff from its INDEX sha instead. They also yank the TOOLCHAIN mid-review, partially (no `.bin/`/`eslint`/`typescript`; vitest still runs) or totally (`npx vitest` → "Cannot find module 'vitest/config'"). Don't `npm install` on their behalf — substitute proxy greps (`: any`/`as any`/`<any>`, `.only`/`.skip`/`.todo`/`xit(`), never inherit "typecheck clean, eslint 0 errors"; `npm ci` only when the TASK says to, then re-verify the full suite TWICE (a raced install leaves a PARTIAL tree — `ls node_modules/vitest/dist/cli.js` before believing any red suite). Pre-wipe evidence stands if every staged blob is index == worktree AFTER it. Stray `_poc-*.test.ts` files they drop into `src/**` skew the file/test counts; note them, don't delete them.
- **A diff CARVED BY HAND out of a superset you already approved is a NEW review, and any earlier marker is stale by construction.** Two passes: (a) split-damage — grep the WHOLE tree for every symbol the removed half owned, confirm files it CREATED are gone AND unimported, the surviving consumer's types line up (`| null` vs `| undefined`), and no describe block lost its behaviour; (b) re-run EVERY mutation against the current bytes. Findings belonging to the parked half are OUT of scope: say so instead of filing.
- Behavioral equivalence with pre-diff code is the FLOOR of a refactor review, not the verdict — also ask whether the preserved behavior was itself correct ("faithful to the old call-site literals" once approved a live merge-write data-loss bug). If a guard blocks a mutation, hand-trace and report as static-only — never claim a live result you didn't get.

## Mutation-testing protocol (the house method)
- Per criterion: edit the REAL prod file → run → confirm the expected AND ONLY the expected test fails → restore from a scratchpad backup (`diff -q` it byte-identical) → `git diff` shows only the real work → suite green → next. Never `git stash` mid-review (unstages staged files); never `git checkout --` a file that may hold other uncommitted work.
- **PROVE the mutation landed before believing a green run.** `src/**` is MIXED — `page.tsx` CRLF, `nextPath.ts` LF — so a multi-line `perl -0pi -e 's/…\n…/…/'` silently matches nothing and exits 0, and the green suite reads as "no test catches this", manufacturing false gaps. Splice by LINE INDEX preserving each line's own terminator (`text.split(/(?<=\n)/)`, re-attach the matched `\r?\n`); after ANY mutation `grep -n` / echo OLD+NEW. A scripted loop with an unexpanded `$VAR` makes `cp` fail and the next mutation stacks on the previous. `cp`-restore can normalize EOLs — re-check with `git hash-object` vs `git rev-parse :<f>`, not `file`. **`core.autocrlf=true` here**, so blobs are LF while worktrees are CRLF and `git hash-object` applies the clean filter — a worktree/index sha MATCH proves nothing about EOLs. An "EOL-only normalization, content unchanged" claim renders as a whole-file rewrite in `git diff` and must be PROVEN, not assumed: strip `\r\n`→`\n` from BOTH blobs in python and diff those (`grep -c $'\r'` on a piped blob is unreliable in Git Bash and reported 0 CRs for a 132-CRLF blob). BIN-645 r3: the claim held, but the strip surfaced a stray `\r\r\n` that normalization turned into a real extra blank line.
- **`rm -rf node_modules/.vite/vitest` before EVERY run in a mutation loop.** The on-disk transform cache serves the PREVIOUS mutation's module after a `cp` restore, so restored bytes "fail intermittently" (BIN-645: 3 reds in 13 runs, then 24 green). Tell it from a real flake by the SIGNATURE — each phantom red reproduces a mutation already run this session. Never file a flake, and never trust a green, until the cache is cleared. **Grep the mutant BEFORE *and* AFTER the test run inside the SAME command** — the pre-run proof alone is not proof: on this shared checkout a concurrent session restored a mutated `EventCard.tsx` between the pre-run `grep -n` and vitest, turning a mutant that really kills 1/9 into a fabricated "9/9 green, coverage gap found" (2026-08-03, `run(){ echo BEFORE:$(grep …); npx vitest …; echo AFTER:$(grep …); }`). The post-run grep is what makes the record atomic, and it is the ONLY guarantee available in a sprint worktree, which has no local `node_modules` so the cache-clear is a silent no-op (deleting the shared `C:/binge/node_modules/.vite` is unsafe while sibling agents run). **The anomaly also runs BACKWARDS — a restored file can RE-ACQUIRE the previous mutant mid-run**: on 2026-08-07 `movie/[id]/page.tsx` was restored from the scratchpad backup, `cmp`-verified and hash-verified equal to the index, then came out of the very next vitest run carrying the PRIOR mutation's `/*MUTANT*/` again (worktree write-back on this shared checkout, not an edit this session made). The tell was an IMPOSSIBLE result — a tv-only mutation reddening the movie route's cases too, when each route's mutation had been shown to redden only its own. So treat any cross-target failure pattern as a contamination signal before treating it as a coverage fact, and bracket EVERY run with `md5sum` on ALL mutation targets (not just the one you patched); a rerun with clean before/after hashes gave the correct 3-of-6. **Mutate in an ISOLATED worktree built FROM THE INDEX whenever siblings share the checkout** (a prior round's mutant reached the coordinator's index mid-staging) — `TREE=$(git write-tree); C=$(git commit-tree $TREE -p HEAD -m review); git worktree add --detach <scratch>/wt-r<N>-<HHMMSS> $C`. **Give it its OWN `node_modules` via `npm ci --prefix <wt> --no-audit --no-fund`** — 42 s / 722 packages on a warm cache, verified 2026-08-08 — and NEVER a `mklink /J` junction back to `C:\binge\node_modules`: the junction emptied the shared toolchain THREE times in one day (a `git worktree remove --force` follows it; the third was fired by a SIBLING session cleaning up a leftover worktree, and `npm ci` to self-heal was then REFUSED by the classifier, so recovery was not even mine to do). Its own install also makes the cache genuinely isolated with no `cacheDir` override. Teardown with a real `node_modules` fails as `error: failed to delete …: Filename too long` — that is EXPECTED and non-fatal: the worktree is already unregistered (`git worktree list` no longer shows it), so follow with `rm -rf <wt>` and assert `ls C:/binge/node_modules | wc -l` is unchanged (448) plus `node_modules/.bin/vitest` present, before AND after. Delete any leftover worktree of your own so it can't bait another session's `--force`, and leave a SIBLING's registered worktree alone. If the shared tree does get emptied: `npm ci` in `C:/binge` restores it (~50 s), re-pin every staged sha, and REPORT it in the verdict; refs and HEAD are untouched, the review's own evidence stands if every run finished before teardown. A shared tree being reinstalled under you surfaces as `Test Files no tests` or `Cannot find module '@exodus/bytes/encoding-lite.js'` from inside jsdom: `ls node_modules | wc -l` before believing ANY result (435 → 58 → 468 → 448 within one review), discard those runs as artifacts, and when `node_modules/.bin` is missing while `node_modules/vitest/dist/cli.js` exists, run `node node_modules/vitest/dist/cli.js run --config …` instead of `npx vitest`. **The junction makes the isolation FAKE unless you also override `cacheDir`**: Vite's default is `node_modules/.vite`, which the junction points straight back at the SHARED tree. Drop a wrapper config in the worktree — `import base from './vitest.config'; import { defineConfig } from 'vitest/config'; export default defineConfig({ ...(base as Record<string, unknown>), cacheDir: '<scratch>/vcache' })` — run with `npx vitest run --config vitest.review.config.ts`, and confirm the real `node_modules/.vite` mtime never moves. Restore mutants there with `git checkout -- <path>` (legitimate ONLY in the isolated worktree, which holds no other work). **An isolated `cacheDir` is still NOT enough**: the same M3 mutant gave three different failure sets in three runs there, each time M3's real failure UNION the PREVIOUS run's mutant's failure — that union is the signature. Only `rm -rf <cacheDir>` before EVERY run, mutant and control alike, plus a restore-and-control run after each mutant (expect the full green count back), makes the numbers reportable. And a python/perl replace written with `\n` silently matches ZERO in a CRLF worktree: make the mutator exit NONZERO on `count != 1` and `grep -n` the result, or the `&&`-skipped mutation followed by a suite run reads exactly like a surviving mutant (hit live 2026-08-08 — a `tmdbId={tmdbId}\nwatched={watched}` pattern; the `\r\n` form landed and was red-alone).
- **Never mutate `firestore.rules` in place** — killed mid-edit agents have left it broken, and a concurrent session can and does mutate the SHARED live file mid-review (verified live, BIN-624, 2026-08-05: a `/* MUTANT: … && */ true` appeared in the worktree copy — unstaged, never Edit-tool-applied by this session — between a "clean control" run starting and finishing; the run's own "Unused function" rules-compiler warning was the tell that the file was already mutated when read, even though the run still reported all-green because Node's `readFileSync` had already captured the pre-mutation bytes in `beforeAll`. RESTORE FROM BACKUP IMMEDIATELY on any such sighting — `git status --porcelain firestore.rules` showing unstaged `M` you didn't make, or a "Change detected, updating rules… WARNING Unused function" on a run where the function should be referenced, both mean the live file moved under you). The reliable fix is a scratchpad COPY, never the tracked file: copy `firestore.rules` to scratch, apply the mutation there, and run the EXISTING test file (copied, not edited in place) with its `readFileSync(...)` line repointed at the scratch copy's absolute path. Running that copy needs its own emulator + config, since `vitest.rules.config.ts`'s `include: ['src/test/rules/**/*.test.ts']` won't pick up a file outside that glob and a bare scratch-dir `vitest.config.ts` can't resolve `vitest/config` (no local `node_modules` there) — the worked recipe: drop the copied+repointed test file INSIDE `src/test/rules/` under a throwaway name (`__ticket_mutant.test.ts`, untracked, delete when done, give it a distinct `PROJECT_ID` string so it can't collide with a concurrently-running suite on the same emulator/project), then `firebase -c <scratch>/firebase.json emulators:exec --only firestore --project <distinct-id> "npx vitest run --config vitest.rules.config.ts src/test/rules/__ticket_mutant.test.ts"`, where the scratch `firebase.json` sets an offset port (8091/4491/4592) so it can't collide with a sibling session's own emulator either. **The plain `npm run test:rules` CONTROL run needs the exact same offset-port treatment whenever a concurrent session holds 8080** — the firestore emulator does NOT silently no-op on a taken port, it hard-fails loudly (`Could not start Firestore Emulator, port taken`, non-zero exit, zero tests run) and is easy to mistake for a red suite; only the hub (4400) and logging (4500) emulators silently reassign to a fallback port, which is what "no-ops" actually referred to. So run the control via `firebase -c <scratch>/firebase.json emulators:exec --only firestore --project <distinct-id> "npx vitest run --config vitest.rules.config.ts"` too (rules path in that scratch config pointing at the real tracked `firestore.rules`, distinct port from the mutant run). `md5sum`/`git status --porcelain` the real `firestore.rules` before AND after EVERY run — control and mutant alike — not just before, AND ONE LAST TIME immediately before writing the verdict, since the file can and does move again in the gap between your last run and typing "pass" (recurred a THIRD time in the same session, at the final pre-verdict check, after two already-caught-and-restored occurrences — BIN-624 round 3, 2026-08-05). Treat every hash check as a fresh assertion for the whole review's duration, never a cached one, and never end a review on a status you read more than a few tool calls ago.
- Mutate the CALLER performing the side effect, not only the extracted helper — a helper can be immaculate while the Firestore write is unpinned. **A stamp-DECISION composition at a call site is a separate mutation target from the shared derivation the same diff already swept** — BIN-814 (2026-08-10): `shouldStampProvidersAtAdd` gained an 8-test dedicated describe block (`tmdbFieldsRefresh.test.ts`) covering the pure function exhaustively, but its ONE call site — `WatchlistContext.tsx`'s `addItem`, `shouldStampProvidersAtAdd(isNewAdd, item.providers, item.subscriptionProviders ?? undefined)` — has zero coverage in `WatchlistContext.test.tsx`: reverting the call to the pre-ticket 2-arg form (dropping the third argument entirely) left the file's full suite **91/91 green** (verified live). Root cause, and the tell to check for: the test harness's own `newTitle()`/`addItemRef` types explicitly `Omit<WatchlistItem, … | 'subscriptionProviders'>`, so no fixture in the file can even SUPPLY the field — the harness type was mechanically widened to keep the file compiling, which silently forecloses the very case that would catch the regression. Widen the Omit list back (or add a differently-typed fixture) and add a case: settled snapshot + not-in-library + `providers` AND `subscriptionProviders` both real arrays → `providersCheckedAt` stamped; same `providers`, `subscriptionProviders` omitted → NOT stamped. Also mutate a `useRef` mirror back to the closure state var (BIN-593). A shared ref carries MULTIPLE write sites — grep every assignment, mutate EACH. Mutate duplicated constants too. **Mechanical sweep across N sibling mutators** (BIN-598): diff the harness's ref list against the production export list — a function in NEITHER has ZERO coverage (**a filed sweep-gap does NOT close itself** — re-run the revert every round). A "one test per mutator, on purpose" comment is a CLAIM to re-verify by counting, not trust: `WatchlistContext.tsx`'s BIN-598 migration (`items.find` closure → `findItem(itemsRef.current, …)`, dropping `items` from the dep array) touches **nine** `findItem(itemsRef.current` call sites (`addItem`, `updateStatus`, `updateWatchedAt`, `updateRating`, `updateNotes`, `updateProgress`, `updateTmdbStatus`, `setRuntime`, `refreshTmdbFields`). First found (2026-08-01) with `updateNotes`/`refreshTmdbFields` uncovered (reverting both left 63/63 green); CLOSED same day with one alone-red `it('BIN-598: … (X)')` per site. Grep every `findItem(itemsRef.current` call site and cross off one named test per site; an uncrossed site is the gap, however confident the framing comment sounds, and on a RE-review re-run the COUNT — a new mutator lands uncovered while the original names still check out. **RECURRED 2026-08-04, predicted exactly**: the SAME file's next round migrated `updateRating`/`updateNotes`/`updateProgress` from `items.find` to `findItem` alongside `updateWatchedAt`/`updateTmdbStatus` (the two the describe-block title actually names, each with a dedicated "reads the LIVE snapshot" test). - No rules-test update is owed when `git status` shows no `firestore.rules` change and a grep of the changed collection against the rules diff shows zero overlap. A comment asserting a rules-safety OR a REACHABILITY claim gets verified against the actual predicates, never trusted, and **re-verified every round it is rewritten, including a claim stated as a PROPERTY** ("a caller that does not state intent must not count, reachable or not" still carries a residual factual half — grep that too). BIN-641 burned four rounds of these (a cited `OnboardingFlow.handleAdd` caller an `alreadyAdded` chip makes unreachable; a correct sedd→sedd claim resting on every `updateStatus(...,'sedd')` caller). Re-grep the LIST each round; it changes.

## GDPR, PII, deletion & money guards
- Deletion-cascade correctness is proven by RUNNING the emulator rules suite, not by tracing refs into the delete batch. A compile-time field-coverage gate is classification ONLY; pair with skip-set pinning (BIN-328). Greps prove PRESENCE, not deletion reachability. New user-owned subcollections flow through `KNOWN_USER_SUBCOLLECTIONS`. A destructure-before-write strip needs a key-absence assertion (BIN-505). Cross-check a shipped schema/listener against its binding review-panel plan doc — tests get "deliberately extended" to legitimize a vetoed design.
- Money/catalog: never hardcode a live catalog-derived price — compute it from the lookup at assertion time (recurring BIN-403). Alias-map mirrors (functions vs src): derive expected from the single source of truth, mutation-test BOTH drift directions (BIN-420). Resilience claims get checked at CALL SITES (BIN-430/442). A test hardcoding an unexported const must NAME it in a comment.

## Legitimate update vs cover-up
- Legit: the diff visibly implements the new contract, assertions stay strict, no unrelated assertion touched (BIN-16/17). **A strict→REGEX relaxation is an honest environment accommodation, not a weakening, only when THREE things hold and you PROVED the first**: the framework really does normalize the value (probe it — swap the exact form back in and READ the `Received:` line; `next/link` renders `entryHref()`'s `/tv/1399/` as `/tv/1399` in jsdom), the exact string is still pinned in the producing helper's own test (`src/lib/calendar/entry.test.ts` `toBe('/tv/100/')`), and the component consumes that helper VERBATIM with no re-derivation. Check the loosened form still discriminates what it names (`/^\/tv\/1399\/?$/` still pins media type and id). Strict→different is legit only when production changed FIRST for a real reason — the old behavior genuinely gone (no dead sort/cap/slice, or the asserted line DELETED) AND the new fixture fails if it returned (BIN-360/601). **A test rewritten to assert the OPPOSITE (the strongest form of this) needs four things, all four checkable in one mutation pass** (BIN-679, 2026-08-08, both accepted: `{season:0,episode:2}`→`toBeNull()` and "ZERO checkboxes"→"checkboxes exist"): the reversal is (i) equally strict, not looser; (ii) accompanied by a NEW case so the file GROWS (+1 `it` here, the un-mark path the reversal opens); (iii) red against the OLD behaviour re-applied — mutate the new guard OUT and require the rewritten case to fail (4/37 here); and (iv) the ban's stated REASON is genuinely dead, verified in code and not from the diff's own comment. On (iv) also grep for OTHER live paths to the banned state before crediting a "this was unreachable dead code" claim — season 0 was already tickable via `SeasonPageClient` on a hand-typed `/tv/<id>/sasong/0/`, and `useMarkSeen` still writes `last_episode_to_air` (a special for Doctor Who 2005) straight into the marker, so the reversal was a live FIX on more paths than claimed rather than the activation of dead code. Cascade row: every full-array `.toEqual` must GROW — shrinking is the cover-up signal (BIN-175). Retiring a fn: old export gone EVERYWHERE (BIN-178); dropping assertions for a schema-removed field is correct (BIN-292). VERDICT vs OUTCOME conflation (judged `clearable` vs committed `cleared`) can look like a weakening — trace the increment SITE; a pass-through cross-check is vacuous (BIN-566). A `deleteDoc` bump 1→2 is legit when BOTH exact paths are pinned (red flag: downgrade to `toHaveBeenCalled()`); guard+migration ship atomically (BIN-356).
- **Reverts get their own protocol, not mutation-testing:** blob-hash the index against the revert target; diff exported-symbol lists; test-count delta must equal the removed prod tests. Zero-test code reverted removes zero coverage. **In-batch revert** (undone pre-commit) leaves no trace in `git diff --cached`; confirm via `git show HEAD:<path>` and mutate the REJECTED design back in (BIN-593).

## When NO new test is owed
- One-line non-branching discriminants in hooks (`!snap.exists()→'ghost'`, bare `catch→null`) over a tested pure helper (BIN-21); prop-threading, conditional JSX, ARIA spreads, Set toggles (BIN-42); `useMemo`-only optimizations, zero-logic components (BIN-336); a JSDoc MOVED to the fn it describes or CORRECTED to drop a symmetry the code lost (BIN-616/618) — verify by running both copies. Byte-identical delegation to a tested helper (incl. a filter clause inert because a downstream `continue` already dropped it — READ that fn); a signature change threading its new param; pure I/O consolidation over a tested decision fn (BIN-541). Forward-prep with no reachable path; a defense-in-depth guard on a provably unreachable condition — don't demand a first RTL harness over one boolean loading-gate (BIN-596/595/601). **A HARNESS hardening is the same class and gets the same verdict — hygiene, unpinnable, file nothing either way, but characterise it rather than guessing.** BIN-823 r9 moved `delete process.env.SELECTION_ALLOW_THIN` into `beforeEach` beside the existing `afterEach` copy, against a leak from another FILE in the same worker (vitest runs files sequentially in one process, so `process.env` really does carry over). Three-point probe, not one: inject the leak at MODULE scope in the test file (it runs before any hook) and run with (P1) both hook deletes → green; (P2) only the `afterEach` → still green; (P3) neither → the two throw cases red 2/10. P2 is the informative one — with an `afterEach` present a cross-file leak can only reach the file's FIRST test, so the `beforeEach` is protective in principle and observable in none, and its comment must not claim more than that. Same reasoning wherever a fix hardens the harness rather than the code: the honest report is "correct, strictly more robust, not mutation-detectable today", with the mutation you ran to say so.
- When such a gate DOES get an RTL harness (BIN-596/645), mutate each layer separately — `current = notReady ? null : getItem(...)`, `disabled={notReady}`, each handler early-return, the refusal toast, the signed-out route (removed AND wrong path), BOTH terms of the auth gate. Mirror fixtures into BOTH siblings (QuickAddButton + StatusButton). The signed-out test must assert three things together — route taken, remembered return path (exact string, `.search` included), and the OLD consent-bypassing `signIn()` NOT called — and keying `signedOut` on the Firestore profile instead of `uid` must go red (verified BIN-645). Once `disabled={authLoading}` lands, BOTH in-handler auth guards (`signedOut`'s `!authLoading` and `handleRemove`'s copy) are unreachable — don't call either load-bearing, and don't file the green mutation; see the disabled-button rule. **"Exact string, `.search` included" must be checked PER SIBLING, not once per pattern**: BIN-668 copied the same `rememberNextPath(window.location.pathname + window.location.search)` handler into TopbarActions AND HomePageClient's landing CTA, but only TopbarActions' fixture set a query (`/search?q=dune`) — HomePageClient's fixture stayed on bare `/`, so dropping `+ window.location.search` there passed 8/8 green (verified live). Low severity only because the home route never carries a meaningful query today; flag it, don't block on it, and re-check the moment `/` grows a query-driven view state.
- **Mocking the provider hooks pins the COMPONENT and leaves the PROVIDER's state machine unasserted** — `vi.mock('@/hooks/useWatchlist')` full-replacement is fine for exactly that scope, no more. Mutate the provider facts the component tests assume: `useState(true)` for `loading` → `false`, and any "deliberately stays true" branch (BIN-601's onSnapshot error handler) → `setLoading(false)`; both left 49 green. Owed: `loading` assertions in the file rendering the REAL provider — true before the first snapshot, false after, false for a null uid, still true after an error callback. **A DERIVED boolean the provider exposes (`libraryKnown = snapshotSettled && !listenerFailed`) must be mocked as a GETTER computed from the same two primitives, never a settable literal** — a literal lets a test set `listenerFailed: true` and still hand the component `libraryKnown: true`, a combination production cannot produce, silently voiding every gate assertion in the file (BIN-596's CollectionSection/QuickAddButton mocks both do this correctly: `get libraryKnown(): boolean { return this.snapshotSettled && !this.listenerFailed; }`, byte-identical to `WatchlistContext.tsx`'s own derivation — grep-diff the two formulas, don't just eyeball them). Being getter-only also makes an accidental `watchlist.libraryKnown = true` in a test throw (strict-mode ES modules) rather than silently no-op. Confirm reachability, not just the formula match: check each of the 4 boolean combinations is independently producible by the real onSnapshot success/error callbacks — the easy-to-miss cell is "listener fails before ever settling" (`snapshotSettled: false, listenerFailed: true`), reachable when the FIRST snapshot attempt errors. Verified live 2026-08-04 on CollectionSection.test.tsx: comprehensively reverting every `mounted && libraryKnown` gate to bare `mounted` in the production file fails 3 of its 5 dedicated tests alone (not the 2 a prior report claimed — always re-run the count rather than inheriting it, even when the direction is "more covered than claimed").
- **Two exceptions override the exemption above:** (1) the ticket lists a test as an acceptance criterion — an unmet self-imposed bar is a gap even in an exempt shape; extracting the buried decision (BIN-599 → BIN-611's `planQuickRateWrite`) is only HALF the remedy, since the helper's verdict is inert until the CALLER is pinned obeying it. (2) the gate protects a counter/date the code calls permanent-and-uneditable (`rewatchCount`, `watchedAt`) — earns a test at one-boolean size; reserve the exemption for gates whose failure is a redundant render, not silent corruption.

## Rounding, jsdom, TZ/DST
- Rounding oracles need `.5`-exact fixtures (`79/2=39.5`: round=40 vs floor=39) (BIN-87); `Math.round(x*2)/2` with only an `x>0` guard snaps 0.25 to 0 — probe `0.1`. jsdom `getBoundingClientRect()` is always a zero DOMRect.
- **`fireEvent.click` on a `disabled` button fires NO handler**, so adding `disabled={cond}` RETROACTIVELY hollows out an existing case's post-click assertions: a mutation that used to go red goes green. Verified twice (BIN-645). So on any diff adding `disabled`/`aria-disabled`, RE-RUN the prior round's handler mutations rather than carrying the verdict. Usually NOT a gap: the in-handler guards become unreachable behind an attribute the same case pins (`toBeDisabled()` goes red if removed) — accepted defense-in-depth — but the comments must stop claiming to prove handler behaviour.
- A DST guard is real only if the buggy fixed-ms path yields a DIFFERENT calendar date at that fixture — spring-forward never crosses local midnight (tautologically green), so anchor across FALL-BACK (Sun 2026-10-25) and assert the exact ISO under `TZ=Europe/Stockholm`. Floor BOTH sides to local midnight for whole-day diffs (BIN-145); pick an instant where zones disagree (23:30 UTC = next day CEST) (BIN-105/350).

## Parsers, regex, dispatch, lookup tables & SEO
- `\d+` parsers: test the syntactically-valid-but-semantically-invalid boundary (`/movie/0` → null); strict-digit hardening needs empty-string and phantom-id-0 cases (BIN-560). Regex tightening: a NEGATIVE + POSITIVE pair per pattern — negative-only passes even if the regex reverts (BIN-176); anti-over-rejection tests are as load-bearing as the reject side. `\b` after a hyphenated token false-matches `accent-soft` — use lookarounds.
- Ordered dispatch: the ordering test uses a path matching an early branch correctly and a later one incorrectly (BIN-345). `as Record<string, any>` trips CI's `no-explicit-any` — cast the narrowest slice; `npx eslint` new test files (warnings OK, errors block).
- Alias tables: one exhaustive identity loop (every entry × every alias) covers current AND future aliases (BIN-64/90). An ALLOWLIST needs a fixture per MEMBER, not just per rejected value: BIN-645's `RETURN_QUERY_KEYS` was reject-side pinned (adding `'invite'` → red) yet DELETING `'row'` left 25/25 green while killing that surface's return path. Name every member in the keeps-it case; one added `expect` makes the deletion red-alone — re-derive PER MEMBER, not once (`q` reddens 2 cases, `status`/`provider`/`row` 1 each).
- **A URL/route fixture is a factual claim: grep it back to the line that BUILDS it.** Plausible-looking invented routes recurred EIGHT times across BIN-640/645, once inside the fix for the previous one. Check three things per fixture — the route directory exists under `src/app/`, the query KEY is read by that page, and the query VALUE is one the app can actually produce: `/rekommendationer/?row=2` was wrong on all three (`RecRow.tsx` builds `` `/recommendations/?row=${encodeURIComponent(rowSpec.rowKey)}` `` and `rowKey(id)` is colon-joined, so `?row=person%3A1245`), and `/my/all?status=sedd` was wrong on two (`NumberedActionsList` builds `/my/series?provider=N&status=behind`; `WatchlistPage` only honours `?status=` when `status==='mina'`, i.e. `/my/series`). A fixture that names a surface the app never had keeps passing after that surface moves, so it pins nothing. Curated domain id lists get cross-checked against external ground truth AND the enums/label maps they derive from. Sitemap: two-sided enumeration with REAL constants + an auth/noindex-leak scan (BIN-337/305). **Same discipline for a rejected-Error fixture feeding a message-sniffing branch (`err.message.includes(CODE)`): grep the fixture's string back to the line that actually THROWS it, not to the constant's declaration alone.** BIN-777's `DeleteAccountSection.test.tsx` first shipped `new Error(STALE_SESSION_PREFLIGHT)` — just the bare code — when the real thrower (`AuthContext.tsx:991`, `` throw new Error(`${REQUIRES_RECENT_LOGIN} (${STALE_SESSION_PREFLIGHT}): …`) ``) puts BOTH codes in one message on purpose, specifically so a caller sniffing in the wrong order can't tell them apart. A fixture with only the narrow code is reachable under EITHER branch order, so the swap mutant (check `REQUIRES_RECENT_LOGIN` before `STALE_SESSION_PREFLIGHT`) survived 5/5 — closed by rebuilding the fixture as the literal template string the thrower emits (verified live: swap mutant now fails 1/5 alone). Two sibling messages sharing an identical PREFIX (here, a promise-bearing sentence appended only on one branch) additionally want the differing suffix asserted on its own (`toContain` the promise clause / `not.toContain` it) so a prefix-preserving swap can't hide behind the shared substring.

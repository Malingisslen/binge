# binge-code-reviewer — client chapter

### Hooks, effects & closure safety
- **A render bail-out must never depend on a lazily-`enabled` query.** A `return null` keyed on `useSeasonRecaps(..., open)`'s data meant the toggle setting `open` never rendered — feature unreachable. Gate on a signal known before opening.
- **Dep arrays must match the query key's granularity** — an effect on a raw object PROP re-fires on a value-equal re-render although React Query (keyed on primitives) did nothing. One Firestore write usually fires onSnapshot twice (optimistic + ack) with fresh identities.
- **The inverse bites harder: a dep the body never READS can be load-bearing, because the callback's IDENTITY is the caller's only signal.** `setRuntime`/`refreshTmdbFields` bail on an empty library while their title-page effects key on nothing watchlist-derived, so on a cold load they last run BEFORE the first snapshot; dropping `items` from those `useCallback` deps no-oped the BIN-93 backfill for a whole visit (BIN-598). Before "cleaning up" a dep, grep each caller's effect deps for a watchlist-derived value; if none, keep `items` (eslint-disable) + a "new identity when a snapshot lands" test.
- **An effect that CONSUMES state must be idempotent, and a single-use read isn't.** `takeNextPath()` (read+remove) in the login redirect effect: `reactStrictMode` is ON by default in Next 16, so run 1 consumes and pushes the remembered path, run 2 reads null and pushes the DEFAULT, which wins. Same shape when a dep takes a second identity while still mounted. Latch with a `useRef` (it survives the remount). Check the value's LIFETIME too — an abandoned sign-in leaves it in `sessionStorage` for the whole tab.
- Optimistic/blur races: mirror the field in a `useRef` set SYNCHRONOUSLY before the `await`, re-sync in an effect, roll back identity-checked — `useOptimisticMirrorField`.
- **A user-facing CONFIRMATION computed from the render closure, beside a write computed from the live ref, can lie.** BIN-641's "omtitt räknad" toast reads `getItem()` while `addItem` reads `itemsRef` after `await fsdb()`: a remote status change/delete in that window makes the toast claim a count that never happened. A `current != null` guard proves a snapshot LANDED, not that the write saw the same row — and it is only null-safety when the shared helper already returns `{}` for `undefined`. Say which direction is reachable (the UI-gated one usually isn't) and whether the residual is cosmetic or data.
- **Sync-ref-before-await fixes same-operation double-fire ONLY**, not cross-operation staleness: a module cache written AFTER an `await` from pre-await data can land after a concurrent mutation's invalidate and re-poison it (`syncProgressToGroups` vs `createGroup`). Ask: "can a DIFFERENT mutation invalidate mid-flight, and does this write compare freshness before landing?" — same for an effect-driven auto-retry beside a re-entrant manual call of that mutation (BIN-587's remedy: pre-await epoch bump + post-read `isCurrent()` + in-flight counter + a once-per-uid latch re-armed on a `uidRef`, never per sign-in). **The mirror case bites too: a guard ref marked only AFTER an async write resolves (deliberately, so a failed attempt stays retryable) protects only calls SEQUENCED after that mark, not two INDEPENDENT calls started concurrently before either's mark lands.** BIN-954's `addedByProgressRef` (marked post-`upsertTitle`, by design — see the addedAt-repair/notes-migration bullet below for why that direction is usually right) still let two rapid episode ticks on the same untracked series both pass the synchronous `known` check and both enter the TMDB-fetch-then-add branch — confirmed by instrumenting the branch entry (both fired) with no UI disabled-state or lock between the two `void handler()` fire-and-forget calls. Ask the mark-timing question in BOTH directions: "can a second independent call start before this one's mark lands?", not just "does a retry see the mark". **The same guard also races against a DIFFERENT mutation that deletes what it marks.** BIN-954 round 3: `removeItem` prunes `addedByProgressRef` synchronously after its own `deleteDoc` resolves, but a concurrent in-flight add's mark lands strictly AFTER (post-`upsertTitle`) — so a remove issued while an add is still writing (reachable: Firestore's local-cache echo shows the new row, hence a "Ta bort" control, before the add's own promise settles) can have its prune run BEFORE the add's mark, leaving the ref stale-"present" over a doc the server actually deleted (writes to one doc from one client apply in issuance order, so create-then-delete lands deleted). The next progress write then reads `known=true` and merge-writes the exact fragment this ticket removes. Ask the cross-operation version too: "does a SIBLING mutation's cleanup run inside this mark's own async window?"
- **Every session dedupe Set/Map key needs the same discriminants as the `.find` beside it.** Include `uid`; reset on uid change; UN-mark in `catch` and rethrow so a failed commit doesn't opt an id out of a PII migration.
- An eager migration effect deduping only on async listener state re-fires mid-batch — needs the sync ref. Cross-account guard: set `itemsUidRef.current = uid` synchronously in onSnapshot before `setItems`, and gate migration effects on it.
- **Removing an "accidental" error state can break a caller relying on it as a circuit-breaker** — the ghost-member rollback re-armed `GroupPageClient`'s uncapped auto-join into a write-storm.
- **An eager (ungated) fan-out still needs the reference's `isLoading` branch** — dropping it with the `enabled` gate renders a false "hittade inget" mid-fetch; eager fetching overlaps interaction, so the guard matters MORE.
- A `permission-denied` TERMINATES an onSnapshot (no retry) — an opt-in write that flips read access needs an explicit epoch-bump resubscribe. **An `onError` that deliberately leaves `loading: true` is the right DATA call and an incomplete PRODUCT one**: not publishing an empty library as settled truth is correct, but it makes the failure a permanently-spinning app behind a `console.warn`. Require a visible error state + resubscribe, and check the warn TEXT matches what was suspended.

### React Query caching mechanics
- `prefetchQuery` carries the SAME `staleTime` as the consuming `useQuery`; per-title keys stay OUT of `PERSISTED_QUERY_PREFIXES` (5 MB).
- v5: `enabled:false` → `status:'pending'`/`fetchStatus:'idle'`, so `isLoading` is FALSE. `isPending` also settles false on ERROR, so "not yet resolved" is `!isSuccess`. A background refetch error keeps `.data` while flipping status — render-branch order is a second guard. `enabled` does NOT narrow the closure's TS type; default `gcTime` ~5min regardless of `staleTime`; keys stable BY VALUE.

### GDPR, PII, auth & legal disclosure (bias to keep)
- **EU AI Act Art. 50:** the AI-generated label must be legible NEAR the content. When a refactor turns ONE toggle covering N items into N toggles, a group-level disclosure must MOVE per-item. `DisclosedRecapProse` is the sole emission site. CC BY-SA (ADR-0011): render nothing when `sources.length === 0`.
- Untrusted wiki text: `validateRecapText` is defense-in-depth; the real controls are plain-text rendering (never `dangerouslySetInnerHTML`) and `safeHref` (`^https?://`).
- **Spoiler safety:** the cursor is the CONTIGUOUS-from-start frontier (`contiguousWatchedBoundary`), NEVER `max(watched)`. Prior-season fetch sets derive from `coveredBoundary`, excluding its own season; specials (`season < 1`) excluded at every layer; the fallback walk-back decreases monotonically, capped at `MAX_FALLBACK_STEPS = 3`.

### Provider catalog / cost model (money)
- The live cost signal is `resolveEffectiveMonthlyCost` (tier → custom → campaign), not catalog `defaultMonthlyCost` — resolve once per provider, reuse for status + `monthlyCost`. `isFree` survives a custom cost.
- Provider retirement into an alias: `git grep <retiredId>` across `src/` is mandatory — `SEO_PROVIDER_IDS`/NL-regex→id tables are NOT auto-safe, and a removed tier id reprices users.

### Design tokens & a11y
- **A bare colour-token name in a className is a silent no-op, not a legacy alias.** `surface` lives under `theme.extend.colors`, so only `bg-`/`text-`/`border-surface` generate. Same for `bg-2`, `rule`, `acc-deep`.
- `<div role="checkbox">` needs `tabIndex={0}`; `role="tooltip" id="X"` needs `aria-describedby`; saffron `:focus-visible` is functional a11y, not a two-accent violation; `role="option"` must be Arrow-key reachable.
- **Moving focus INTO a card that clips needs an INWARD ring.** globals.css draws `:focus-visible` 2px OUTSIDE the border box, so once the focusable element is an inner child of an `overflow: hidden` root (`.ev`, `.prow`, any rounded card) the ring is clipped on three sides. `focus-visible:[outline-offset:-2px]` is the correct fix and it DOES win: Tailwind v3 flattens `@layer` and emits arbitrary/variant utilities LAST, and `.x:focus-visible` (0,2,0) beats bare `:focus-visible` (0,1,0). Prove a new arbitrary utility actually generates — `npx tailwindcss -i src/app/globals.css -o <tmp> --content <file>` + grep — before accepting it; a className-only test pins the string, never the cascade.
- **A shared modal shell's document-level capture listeners order by MOUNT, not by which dialog is topmost.** Two listeners of the same phase on the same target run in registration order (verified in jsdom: capture always precedes bubble regardless of add order, but two captures run first-added-first) — so if a second `DialogShell` ever mounts while a first is still open, the OUTER (earlier-mounted) dialog's `Escape` capture-listener fires and `stopImmediatePropagation()`s before the INNER (topmost, later-mounted) one ever sees the key, closing the wrong dialog. `DialogShell` (BIN-1261) has this defect but it is not reachable today — its only two consumers, `ConfirmDialog`/`HandOverGroupDialog`, are wired so one's full-screen overlay blocks opening the other. Flag it non-blocking until a THIRD consumer legitimately stacks two `DialogShell`s; the fix is a shared LIFO registry so only the topmost instance's listener acts.
- **Un-nesting a control out of a card-wide `<Link>` must hoist ONLY the interactive branch.** Interactive content inside `<a>` is invalid and the `preventDefault`/`stopPropagation` it forces is the tell — but check the ELSE branch: BIN-660 hoisted the non-interactive footer too, so movie cards lost ~27px of navigable surface and flipped `cursor: pointer`→`default`, against the ticket's own "no visual change". A span blockifies as a flex item, so a `block` class "restoring the box model" is a no-op claim. Re-derive spacing against globals.css (a flex `gap` and a child `marginTop` ADD) and scope the compensating value to the TOGGLE BRANCH; the cascade is unpinnable in jsdom but that inline style is not — assert it in BOTH branches.

### Static export, routing & SEO
- `usePathname()` returns the real browser path even under the catch-all rewrite but EXCLUDES the query — a "come back where I was" feature keyed on it drops query-only state (`/search/?q=`). Use `location.pathname + location.search` in the click handler (no `useSearchParams`/Suspense cost under `output: 'export'`). Title routes are `/movie/:id/`+`/tv/:id/`, search is `/search/?q=`, recs are `/recommendations/?row=`; a comment or fixture naming `/film/…`, `/sok` or `/rekommendationer/` pins a path the app never produces — `ls src/app` before believing a Swedish-looking route name, and check whether a sibling marker copied it.

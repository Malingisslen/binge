### Static export, routing & SEO
- Any `src/app/**` page with only static segments pre-renders to `out/**/index.html` — NO `DynamicRouter.tsx` entry, NO rewrite; only `src/app/[...path]/` needs those. With `dynamicParams=false` an unlisted id falls to the SPA catch-all, rendering noindex/NotFound as a **200, not a 404**. `generateMetadata`'s early `return {}` inherits the INDEXABLE root default.
- A sitemap-committed URL must render a 200 `EmptyState` with valid JSON-LD, never `notFound()`. Assert sitemap ↔ `generateStaticParams` equality both ways.
- Build-time fetches: each parallel discover call gets its OWN `withRetry` + inner `.catch(() => [])`; `discover` needs `with_watch_monetization_types` beside `watch_region`; `AbortSignal.timeout(8_000)` per retry ATTEMPT, built inside the retried closure, not the 20s `buildSignal` (5×20s exceeds Next's 60s cap). **A deadline must start when the call DISPATCHES, not when it is created.** `AbortSignal.timeout` runs from creation, `pages.map(p => f(p, {signal: buildSignal()}))` creates all N in one synchronous burst, and `client.ts`'s 8-slot semaphore rejects a QUEUED waiter the moment its signal fires — so only ~`timeout/latency × 8` of the fan-out ever issues a request and `Promise.allSettled` swallows the rest into a green build (measured: 64 of 210 dispatch). The victim is whatever enqueues LAST (BIN-815 emptied every `/person/` URL from the sitemap while `person/[id]` still pre-rendered ~1000 — a sitemap/pre-render mismatch is the "Crawled – not indexed" direction; since BIN-823 both read one manifest and `sitemap.ts` fetches nothing).
- **A kill-switch that disables ONE guard leaves the SECOND guard on the same failure path armed.** `SELECTION_ALLOW_THIN=1` zeroes the coverage floor so a preview may build thin — but a `derive` that TIMES OUT with no previous manifest never reaches `writeSelectionManifest`, so `sitemap.ts`'s `selectionOrThrow` fails that build anyway, from a different file with a different message. Trace a new flag to the END of its failure path, not to the guard it names; a build artifact written only on the success branch is the usual second guard.
- **Build INSTRUMENTATION must emit in the FAILING regime, not just under test:** BIN-815's hang-watchdog started only after a cache MISS, but the Monday full refresh + `REFRESH_AFTER_MS`=6d means a mid-week code deploy does ZERO network fetches — the exact runs that hung — so it would have printed nothing. Name the regime the incident ran in, and enumerate the PHASE from Next's own source: `build/utils.js` runs `buildAppStaticPaths` ONLY when `route.dynamicSegments.length > 0`, so `movie/[id]`+`tv/[id]` `generateStaticParams` run in "Collecting page data" (each with its own INLINED `collectIds` copy no shared helper reaches) while `sitemap.ts` (a metadata route, no dynamic segment) runs in the LATER "Generating static pages". Every worker is a separate PROCESS, so an unregistered route's hang surfaces as a sibling worker's healthy `inflight=0` — partial registration is worse than none. **A phase-scoped inference needs a phase MARKER in the line itself:** the same timer keeps ticking after the phase it was reasoned about (`fetchForBuild` restarts it during export), so `inflight=0` printed while sitemap.ts's ~4000 signal-less list calls hang reads as "not the TMDB layer" and is a lie. Registering a call is behaviour-neutral and SEPARABLE from giving it a signal. Next pipes static-worker stderr to the parent without resetting its hanging-worker SIGTERM timer, so a stderr heartbeat is safe.
- **A "stuck call" threshold set ABOVE the call's own abort deadline can never fire on queue backlog** — `semaphore.ts` rejects a queued waiter the instant its signal fires and the `finally` deregisters it, so with `buildSignal()` at 20s and `STUCK_AFTER_MS` 30s a merely-queued call always leaves the registry first. A STUCK line then means "this outlived its own abort", the instrument's highest-value signal — so a comment justifying the report cap with "1000 queued calls would all read as stuck" (or a `(inkl. köade)` suffix) teaches the next investigator to dismiss exactly that line. Keep the cap, fix the justification. **The same sentence goes false the moment an AGGREGATE is registered under one label**: BIN-815 r4 wrapped `collectPersonIds` (~2100 fetches, no 20 s ceiling of its own) in ONE `trackBuildCall` → `STUCK params:person-ids` every tick on a healthy build. Remedy (r5): opt-in `{aggregate:true}` + its own 4-min threshold (healthy ~40 s, since the inner 20 s signals are created in one burst and the queue self-aborts). Per-call registration inside the pipeline is stronger (no flag to forget); a label-derived threshold is worst (silent string drift). An aggregate entry still feeds `oldest=`, so healthy prints `oldest=40s` with NO STUCK line.
- **`deploy.yml` failure semantics, all three verified:** `timeout-minutes` on a STEP kills only that step and marks it failed — later `if: always()` steps still run; only a JOB-level timeout cancels them (parse the YAML and check `jobs.<id>.timeout-minutes` before believing either). `actions/cache@v4` declares `post-if: success()`, hence `Post Restore … = skipped` on every failed build — that line also PROVES the job kept processing steps, so an explicit `actions/cache/save` with `if: always()` DOES cover the step-timeout case; reject a comment calling that "unverified". `github.run_id` is UNCHANGED across "Re-run jobs", so a per-run cache key needs `run_attempt` too.
- **An inner "soft retreat" timeout only retreats if `timeout + remaining work < the enclosing step cap` — check BOTH branches of a two-value pair against `timeout-minutes`, and price the constant rather than accepting a comment that discloses the gap.** BIN-823 r9 shipped `RESCUE_DERIVE_TIMEOUT_MS` 15 min (inside a 45-min step → retreat completes) beside `REFRESH_DERIVE_TIMEOUT_MS` 150 min (inside 175 → ~25 min left for a 90–120 min render, so the run dies as a step timeout anyway). The disclosure was accurate and the outcome harmless, but the LOWER value strictly dominates: at ~45 min the same pathological run warns, keeps the previous artifact and still deploys, while a healthy derive is single-digit minutes (the file's own `AGGREGATE_STUCK_AFTER_MS` comment calls ~40 s healthy) so nothing real is aborted. Derive the healthy duration from a sibling constant's rationale, then say which value the enclosing cap actually permits — and accept "documented, decided with data on ticket X" when the safe window (55–85 min here) is two single measurements away from the only cold floor (44,5 min); a blind pick between two n=1 numbers is not better than a dated ticket. **A runbook remedy's second half is checked against the REGIME FLAG the remedy's own command sets, not against the artifact it saves.** r10 fixed "re-run it, the work is kept" (true) and shipped a false tail — "the types already done are not re-derived" — while its own `-f full_refresh=true` sets `TMDB_SELECTION_REFRESH=1` and `mustDerive = refresh || …` re-derives everything. One cache key holds TWO artifacts (the coverage-floor manifest and the warm `buildCache` details) and r11 then attributed the warm phase to the wrong one, copied verbatim from r10's finding text — write a finding as prose you would accept in the file. Trace the remedy's flag through the code it triggers, every round: r2, r5, r7, r8, r10 and r11 each invented a claim while correcting the previous one. **A MEASUREMENT is scoped to the code path that produced it:** the 2 672 s person derive was measured with a cache-BYPASSING `getMovie` that the SAME commit replaced with `fetchForBuild`, so it still describes an evacuated cache (preview, true cold start) but not the first post-ship push, which restores `.tmdb-cache` via `restore-keys: tmdb-cache-` and reads those ~2 000 cast details warm. Re-scope every quoted number to the regime the NEW code produces before letting prose predict an outcome from it.
